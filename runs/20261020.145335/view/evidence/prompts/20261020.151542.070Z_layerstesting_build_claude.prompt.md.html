Build a command-line cash ledger, an executable named `ledger` at the application root, as
described in `sources/INSTRUCTIONS.md`. It keeps accounts, categories, and cash transactions in a
relational database reached only through the shipped persistence library, enforces atomic commands
and non-negative balances, and reports balances, category totals, and monthly totals.

known answers computed from the seed files. The goal is every check passing.

### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Use the
existing Programmatic Acceptance format: a Python script with assertions against the built
product. Drydock executes each criterion through `languages/python/acceptance/runner.py`; `pytest -q`
runs the project test suite. Retain the criterion ID, observed values, stdout/stderr and result;
an assertion failure fails the check. The harness reports failure operands and available case
counts. Code coverage and persistence interactions require explicit instrumentation; record
available observations as key/value data associated with the criterion. Missing observations
are unknown, not proof that code or an interaction was unused.

### How does this language provide the shared persistence contract?

Use `stack/persistence.md`. Drydock copies `Rigging/languages/python/persistence/{db,sqlite,postgres}.py` and generates
`persistence/{schema,__init__,testing}.py` plus `schema.sql` from `DATABASE.md`. Call
`open_database(dsn)` and `db.<table>.<operation>(...)`; use `persistence.testing.db_session()`
for criteria. SQLite uses the standard library; PostgreSQL needs `psycopg[binary]` in the project
dependencies. Both engines ship together and the DSN selects the engine. Library verification
lives in `tests/test_shipped_database.py`; a Target still verifies its own schema and operations.

# FEATURE: Database Target

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Resolves the database target from the environment and opens it through the shipped persistence library. |
| Depends On  | ARCHITECTURE.md, DATABASE.md |
| Provides    | resolve_database_target() |
| Consumes    | open_database |

## Purpose

Every command needs one database target. `config.resolve_database_target()` returns the setting
that applies by precedence: `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`. The value is
returned unchanged, including any `postgres://`, `postgresql://`, or `sqlite://` prefix, and is
passed to `persistence.open_database` as the DSN.

## Behavior

- If `DATABASE_URL` is set and non-empty, its value is the target.
- Otherwise, if `DATABASE_PATH` is set and non-empty, its value is the target.
- Otherwise the target is `data/app.db`.
- The function reads the environment only. It opens no connection.

## Programmatic Acceptance

=== AC target-precedence ===
Intent: DATABASE_URL takes precedence over DATABASE_PATH, which takes precedence over data/app.db, and each value is returned unchanged.

import os
from config import resolve_database_target

for name in ("DATABASE_URL", "DATABASE_PATH"):
    os.environ.pop(name, None)
default_target = "data/app.db"
assert resolve_database_target() == default_target

path_value = "scratch.db"
os.environ["DATABASE_PATH"] = path_value
assert resolve_database_target() == path_value

url_value = "sqlite://" + path_value
os.environ["DATABASE_URL"] = url_value
assert resolve_database_target() == url_value

postgres_value = "postgresql://ledger@localhost/ledger"
os.environ["DATABASE_URL"] = postgres_value
assert resolve_database_target() == postgres_value
=== END AC target-precedence ===

=== AC target-opens-store ===
Intent: The resolved target opens through the shipped persistence library and yields an empty accounts table.

import os
import tempfile
from pathlib import Path
from config import resolve_database_target
from persistence.testing import db_session

os.environ.pop("DATABASE_URL", None)
scratch_dir = tempfile.mkdtemp()
path_value = str(Path(scratch_dir) / "ledger.db")
os.environ["DATABASE_PATH"] = path_value
target = resolve_database_target()
assert target == path_value
with db_session(target) as db:
    rows = db.accounts.list()
    print(rows)
    assert rows == []
=== END AC target-opens-store ===

## User Acceptance

- None.

## Guardrails

- The target is never opened by this module; only persistence opens connections.
- No default target other than `data/app.db` is applied when either setting is present.

# FEATURE: Date Validation

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Accept only real calendar dates written YYYY-MM-DD. |
| Depends On  | FEATURE-CliEntry.md, ARCHITECTURE.md |
| Provides    | check_date |

## Purpose

Rule 6 of the cash ledger. A date is accepted only when it is a real calendar date in the form
`YYYY-MM-DD`. Impossible dates such as `2026-02-30` are rejected.

## Interface

- `cli.dates.check_date(text: str) -> str` returns `text` when it is a real calendar date in the form
  `YYYY-MM-DD`; otherwise raises `ValueError`.

## Behavior

- The check uses the calendar, including leap years.
- Only the exact `YYYY-MM-DD` shape is accepted; single-digit months or days are rejected.

## Programmatic Acceptance

=== AC valid-date-accepts ===
Intent: check_date returns each real calendar date in YYYY-MM-DD form unchanged, including a leap day.

from cli.dates import check_date

samples = ["2026-01-01", "2024-02-29", "2026-12-31"]
assert [check_date(text) for text in samples] == samples
=== END AC valid-date-accepts ===

=== AC valid-date-rejects ===
Intent: check_date raises ValueError for impossible dates and for every malformed shape.

from cli.dates import check_date

samples = [
    "2026-02-30",
    "2025-02-29",
    "2026-13-01",
    "2026-00-10",
    "2026-04-31",
    "2026-1-01",
    "26-01-01",
    "2026/01/01",
    "",
]
rejected = []
for text in samples:
    try:
        check_date(text)
    except ValueError:
        rejected.append(text)
assert rejected == samples
=== END AC valid-date-rejects ===

## User Acceptance

- None.

## Guardrails

- A date that the calendar does not contain is never accepted.
- Dates are never converted to another format by this feature.
