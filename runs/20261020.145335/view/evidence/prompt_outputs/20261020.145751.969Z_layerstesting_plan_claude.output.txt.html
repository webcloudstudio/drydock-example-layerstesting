# ARCHITECTURE: Cash Ledger

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Module layout, boundaries, and technology decisions for the command-line cash ledger. |

## Questions

- None.

## Purpose

The `ledger` executable is a command-line cash ledger for a small shop. Commands read CSV on
standard output, diagnostics on standard error, and exit codes 0 to 4. Every command runs as one
database transaction. All persistence goes through the shipped persistence library, and the
database is selected by `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`.

## Technology Stack

- Python 3.11 or newer: implementation language. Governed by `python.md`.
- SQLite: database engine, reached through `persistence.open_database` and the shipped SQLite engine. Governed by `sqlite.md`.
- PostgreSQL: selected only by a `postgres://` or `postgresql://` DSN through the same shipped library. Not verified by any acceptance check.
- CLI: the `ledger` executable at the application root. Governed by `cli.md`.
- pytest: test runner behind `bin/test.sh`. Governed by `python.md`.
- POSIX sh: `bin/test.sh`, the `ledger` launcher, and the supplied grader. Governed by `common.md`.

## Module Layout

- `ledger`: POSIX launcher at the application root. It changes to the application root and runs `cli.main` under `.venv`.
- `pyproject.toml` and `uv.lock`: dependency manifest and committed lock file.
- `.venv/`: environment created by `uv venv`.
- `bin/`: POSIX launchers, including `bin/test.sh`.
- `config.py`: database target resolution from the environment.
- `cli/`: `main(argv)` entry point, `cli_runner` test client, command dispatch, and CSV output.
- `commands/`: one module per command group (accounts, categories, transactions, transfers, loads, reports). Each command body runs inside the command transaction wrapper.
- `persistence/` and `schema.sql`: generated from `DATABASE.md` at the DATABASE step.
- `tests/`: pytest suite for the application.

## Boundaries

- Call direction is `cli` to `commands` to `persistence`. The `cli` package never opens a database.
- `commands` reach storage only through `db.<table>.<verb>(...)`, obtained from `persistence.open_database`.
- Application code never imports `sqlite3` or any PostgreSQL driver. Only the shipped engines under `persistence/` do.
- `config.py` reads the environment and returns the selected target as a string. It never opens a connection.
- No command reads `sources/run.sh` or any seed file except through `ledger load`.

## Module Ownership

| Boundary | Owner | Low-level APIs it may access |
|----------|-------|------------------------------|
| Persistence | `persistence/` (generated and shipped) | Driver APIs inside `persistence/sqlite.py` and `persistence/postgres.py` only |
| Configuration | `config.py` | `os.environ` for `DATABASE_URL`, `DATABASE_PATH` |
| File store | None | None. Seed files are read only by `ledger load`, through `commands/` |
| External service | None | None |

## Transaction and Balance Boundary

- The `commands` layer opens one transaction per command and commits it only after every change succeeds.
- Before commit, the balance rule is checked for every affected account. A negative balance rolls the command back and exits 3.
- Concurrency relies on the database's own transaction isolation. No application-level locking is added.

# FEATURE: Database Target

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Resolves the database target from the environment and opens it through the shipped persistence library. |
| Depends On  | ARCHITECTURE.md, DATABASE.md |
| Provides    | resolve_database_target() |
| Consumes    | open_database |

## Questions

- None.

## Purpose

Every command needs one database target. `config.resolve_database_target()` returns the setting
that applies by precedence: `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`. The value is
returned unchanged, including any `postgres://`, `postgresql://`, or `sqlite://` prefix, and is
passed to `persistence.open_database` as the DSN.

## Behavior

- If `DATABASE_URL` is set and non-empty, its value is the target.
- Otherwise, if `DATABASE_PATH` is set and non-empty, its value is the target.
- Otherwise the target is `data/app.db`.
- The function reads the environment only. It opens no connection.

## Programmatic Acceptance

=== AC target-precedence ===
Intent: DATABASE_URL takes precedence over DATABASE_PATH, which takes precedence over data/app.db, and each value is returned unchanged.

    os.environ.pop(name, None)

assert resolve_database_target() == default_target

os.environ["DATABASE_PATH"] = path_value
assert resolve_database_target() == path_value

url_value = "sqlite://" + path_value
os.environ["DATABASE_URL"] = url_value
assert resolve_database_target() == url_value

postgres_value = "postgresql://ledger@localhost/ledger"
os.environ["DATABASE_URL"] = postgres_value
assert resolve_database_target() == postgres_value
=== END AC target-precedence ===

# FEATURE: CLI Entry

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Provides the ledger executable at the application root and the cli.main entry point with its test client. |
| Depends On  | ARCHITECTURE.md |
| Provides    | ledger, cli.main, cli.testing.cli_runner |

## Questions

- None.

## Purpose

`ledger` is the only command-line entry point. It is a POSIX launcher at the application root.
It changes into the application root and runs `cli.main(argv)` under the `.venv` interpreter,
then exits with the returned status. `cli.main` takes an argument list and returns an integer
status. `cli.testing.cli_runner(*args)` calls `main` in-process and returns `(exit_code, stdout,
stderr)`.

## Launcher Contract

```
#!/bin/sh
HERE=$(cd "$(dirname "$0")" && pwd)
cd "$HERE" && exec "$HERE/.venv/bin/python" -c 'import sys; from cli import main; sys.exit(main(sys.argv[1:]))' "$@"
```

# FEATURE: CLI Dispatch

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Routes command words to handlers, rejects usage errors with exit 2, and provides help for every command. |
| Depends On  | ARCHITECTURE.md, FEATURE-CliEntry.md |
| Provides    | command dispatch, ledger --help, ledger <command> --help |

## Questions

- None.

## Purpose

`cli.main` reads the first argument as the command word and dispatches it. Unknown commands,
unknown tables, unknown reports, and wrong argument counts are usage errors: they exit 2, write
nothing to standard output, and write one diagnostic line to standard error. Every command has
help text. `--help` and `<command> --help` write usage to standard output and exit 0. With no
arguments, `main` writes one usage line to standard error and exits 2.

## Commands Recognized

`init`, `count`, `load`, `account` (`add`, `get`, `rename`, `delete`), `txn` (`post`, `get`,
`amend`, `delete`), `transfer`, `report` (`balances`, `categories`, `monthly`).

## Programmatic Acceptance
