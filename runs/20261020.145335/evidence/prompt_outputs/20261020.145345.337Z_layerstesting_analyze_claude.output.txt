# Blueprint Analysis: LayersTesting

## Commander Expectations

- assert the product is an executable `ledger` that keeps cash balances for a small shop in a relational database
- assert every command either completes in full or changes nothing
- assert every report is computed from the database and matches the known answers
- assert the supplied grader `sources/run.sh` exits zero
- assert no account balance goes negative after any command
- assert all persistence goes through the shipped persistence library, selected by `DATABASE_URL`

## Story List

### Feature: Schema and Persistence

| ID | Story | High-level AC |
|---|---|---|
| PERSIST-001 | Resolve the database target | `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`, selects the database; a `postgres://` or `postgresql://` value is a PostgreSQL DSN; other values are SQLite paths with an optional `sqlite://` prefix. |
| PERSIST-002 | Define the three-table schema | `accounts`, `categories`, and `transactions` exist with the keys and references in the Database section; amounts are integer cents. |
| PERSIST-003 | Initialize an empty schema | `ledger init` drops the three tables if present, creates them empty, and writes nothing. |
| PERSIST-004 | Count table rows | `ledger count` writes `table,rows` then the `accounts`, `categories`, and `transactions` rows. |

### Feature: Input Validation

| ID | Story | High-level AC |
|---|---|---|
| VALID-001 | Validate codes, names, descriptions, and memos | Codes are 1 to 12 characters from `A-Z` and `0-9`; names and descriptions are 1 to 40 characters; memos are 0 to 60 characters; none contains a comma or newline; violations exit 3. |
| VALID-002 | Validate and format amounts | Input matches `-?DIGITS[.D[D]]`, is never zero, and has at most two decimals; output has exactly two decimals and a leading `-` when negative. |
| VALID-003 | Validate calendar dates | Dates are real calendar dates in `YYYY-MM-DD`; `2026-02-30` exits 3. |

### Feature: Command Line Interface

| ID | Story | High-level AC |
|---|---|---|
| CLI-001 | Dispatch commands and reject usage errors | Unknown command, table, or report, or a wrong argument count, exits 2 with one stderr line; every command has help text. |
| CLI-002 | Write CSV success output and failure diagnostics | Success writes header and rows as CSV with no quoting, no trailing spaces, and `\n` endings; `init` writes nothing; failures write nothing to stdout. |
| CLI-003 | Provide the `ledger` executable at the application root | An executable named `ledger` at the application root runs each command when invoked by the harness from that root. |

### Feature: Bulk Load

| ID | Story | High-level AC |
|---|---|---|
| LOAD-001 | Load accounts from a CSV file | A file whose header matches `account,name` loads all rows or none; the seed file loads 4 rows; writes `table,loaded` and `accounts,<rows>`. |
| LOAD-002 | Load categories from a CSV file | A file whose header matches `category,description` loads all rows or none; the seed file loads 7 rows. |
| LOAD-003 | Load transactions from a CSV file | A file whose header matches the transaction columns keeps each `txn_id`; any rejected row rejects the file; the seed file loads 120 rows; an unreadable file exits 1. |

### Feature: Accounts

| ID | Story | High-level AC |
|---|---|---|
| ACCT-001 | Add an account | `account add` writes the new account row; a duplicate code or invalid field exits 3. |
| ACCT-002 | Get an account | `account get` writes the account row with its transaction count and balance; an absent code exits 4. |
| ACCT-003 | Rename an account | `account rename` writes the updated row; an absent code exits 4; an invalid name exits 3. |
| ACCT-004 | Delete an account | `account delete` writes `deleted` and the code; an account with transactions is refused with exit 3; an absent code exits 4. |

### Feature: Transactions

| ID | Story | High-level AC |
|---|---|---|
| TXN-001 | Post a transaction | `txn post` writes the new row with id one more than the largest present, or 1 in an empty table; an unknown account or category exits 3. |
| TXN-002 | Get a transaction | `txn get` writes the row; an absent id exits 4. |
| TXN-003 | Amend a transaction amount | `txn amend` changes only the amount and writes the updated row; an absent id exits 4; a negative balance is rejected with exit 3. |
| TXN-004 | Delete a transaction | `txn delete` writes `deleted` and the id; an absent id exits 4; a negative balance is rejected with exit 3. |

### Feature: Transfers

| ID | Story | High-level AC |
|---|---|---|
| XFER-001 | Transfer between accounts | `transfer` writes two `TRANSFER` rows, outgoing first, with the memos stated in the Commands table, or stores neither; the amount is positive and the accounts differ. |

### Feature: Transaction Integrity

| ID | Story | High-level AC |
|---|---|---|
| INTEG-001 | Run each command as one database transaction | Any failing command leaves every table exactly as it was. |
| INTEG-002 | Enforce the non-negative balance rule | After a command's changes and before commit, any account balance below zero rejects the command with exit 3. |

### Feature: Reports

| ID | Story | High-level AC |
|---|---|---|

| RPT-002 | Report category totals | `report categories` writes every category ordered by code, including categories with no transactions, then the `TOTAL` row. |
| RPT-003 | Report monthly totals | `report monthly` writes one row per `YYYY-MM` with transactions, ascending, then the `TOTAL` row. |

### Feature: Verification

## Planning Instructions

### Delivery Shape

The system is a command-line cash ledger named `ledger`, implemented in Python 3.11 or newer over SQLite through the shipped persistence library. Inputs are command arguments, CSV files, and the `DATABASE_URL`, `DATABASE_PATH` settings. Outputs are CSV on standard output for successful commands, one diagnostic line on standard error for failures, and exit codes 0 to 4. The required execution flow is `init`, then `load` of accounts, categories, and transactions, then mutations and reports. Every command runs as one database transaction.

### Test and Acceptance Strategy

Focused story tests are pytest cases against a real temporary database, each story running only the slice it owns and declaring `Suite: scoped`. The supplied grader has no scope selector, so no story runs it. Exactly one terminal story, VERIFY-002, gates on the complete supplied grader and declares `Suite: full`; it depends on every implementation story. VERIFY-001 runs the application's own pytest suite through `bin/test.sh` and is bounded to the suite the application provides. Sea Trial st-001 is the proof of VERIFY-002, and st-002 is the proof of VERIFY-001.
