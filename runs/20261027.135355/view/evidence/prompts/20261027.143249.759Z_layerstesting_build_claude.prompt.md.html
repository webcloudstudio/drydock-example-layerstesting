# Command-Line Application

**Type:** cli
**Version:** 20260920 V1
**Tier:** platform
**Category:** Technologies
**Foundation:** cli
**Description:** Command-line application structure: entry point, argument parsing, exit codes, cross-platform launchers, and testing without spawning a process.

Technology reference. This file does not change between projects.

Prerequisites: `stack/common.md`, `languages/python/python.md`

---

## Foundation Contract

The published shape of this foundation. Drydock synthesizes the story that builds it and every
acceptance criterion writes against these names. Carried verbatim into `cli_compact.md`.

- package: cli
- entry: main(argv: list[str] | None = None) -> int
- fixture: cli_runner
- fixture_source: cli/testing.py

```python
# cli/__init__.py
def main(argv: list[str] | None = None) -> int:
    ...

# cli/testing.py
import contextlib
import io
from cli import main

def cli_runner(*args: str) -> tuple[int, str, str]:
    """Return (exit_code, stdout, stderr) without spawning a process."""
    out, err = io.StringIO(), io.StringIO()
    with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
        code = main(list(args))
    return code, out.getvalue(), err.getvalue()

# conftest.py
import pytest
from cli import testing

@pytest.fixture
def cli_runner():
    return testing.cli_runner
```

A criterion imports `cli_runner` from `cli.testing`, calls `cli_runner("status", "--json")`, and
asserts on the returned tuple. It does not call `subprocess.run`, which measures the installed
console script and the shell rather than the code the story wrote.

---

## 1. Directory Layout

**Rule**: Command code lives in `cli/`. The root holds only packaging and infrastructure files.

```
project/
  pyproject.toml            # [project.scripts] declares the console script
  cli/
    __init__.py             # main() — the single entry point
    commands.py             # one function per command; no argument parsing
    parser.py               # argparse construction; no behavior
  bin/
    run.sh                  # bash launcher
    run.ps1                 # PowerShell launcher
  tests/
```

**Why**: Parsing, behavior, and launching are three contracts. Collapsing them produces a command
that cannot be tested without a shell.

---

## 2. Entry Point and Exit Codes

**Rule**: `main(argv=None) -> int` parses, dispatches, and returns an exit code. It never calls
`sys.exit` and never raises for an expected failure. The console script is the only caller that
translates the return value into a process exit.

```python
# cli/__init__.py
import sys
from cli.parser import build_parser
from cli import commands

def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        return commands.dispatch(args)
    except OperationalError as exc:
        print(f"error: {exc}", file=sys.stderr)
        return 1
```

```toml
# pyproject.toml
[project.scripts]
mytool = "cli:main"
```

**Exit codes**: `0` success, `1` operational failure, `2` usage error. `argparse` already returns
`2` for a usage error; do not override it.

**Why**: A `main` that returns rather than exits is callable from a test in-process. A `main` that
calls `sys.exit` forces every criterion to spawn a subprocess and measure the shell.

---

## 3. Parsing Is Separate From Behavior

**Rule**: `parser.py` builds the `argparse` tree and returns it. `commands.py` holds one function
per command taking plain arguments, not a `Namespace`. Neither imports the other.

```python
# cli/parser.py
import argparse

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mytool")
    sub = parser.add_subparsers(dest="command", required=True)
    status = sub.add_parser("status", help="Report current state")
    status.add_argument("--json", action="store_true")
    return parser
```

```python
# cli/commands.py
def status(*, as_json: bool) -> int:
    ...

def dispatch(args) -> int:
    if args.command == "status":
        return status(as_json=args.json)
    return 2
```

**Why**: Behavior tested through a `Namespace` is behavior tested through the parser. Separating
them lets a criterion call `status(as_json=True)` directly.

---

## 4. Cross-Platform Launchers

**Rule**: Ship both launchers. They locate the environment and invoke the package entry point;
they contain no business logic. A launcher that makes a decision is a second implementation of the
command.

```bash
#!/usr/bin/env bash
# bin/run.sh — locate the environment and hand off. No business logic.
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
if [ -d "$ROOT/.venv" ]; then
    source "$ROOT/.venv/bin/activate"
fi
exec python -m cli "$@"
```

```powershell
# bin/run.ps1 — locate the environment and hand off. No business logic.
$ErrorActionPreference = "Stop"
$Root = Split-Path -Parent $PSScriptRoot
$Activate = Join-Path $Root ".venv\Scripts\Activate.ps1"
if (Test-Path $Activate) { & $Activate }
python -m cli @args
exit $LASTEXITCODE
```

```python
# cli/__main__.py — makes `python -m cli` work identically on both platforms
import sys
from cli import main

sys.exit(main())
```

**Why**: `python -m cli` is the one invocation both launchers share, so the two scripts cannot
drift in behavior — only in how they find the interpreter. `exit $LASTEXITCODE` is required in
PowerShell; without it the exit code is discarded and a failing command reports success.

---

## 5. Output and Streams

**Rule**: Results go to stdout, diagnostics to stderr. A `--json` mode prints one JSON document to
stdout and nothing else. Never interleave progress text into a machine-readable stream.

**Why**: A caller piping stdout to `jq` receives the progress lines too, and the command becomes
unusable in a pipeline.

---

## 6. Testing Without a Process

**Rule**: Test through `main(["status", "--json"])` or the `cli_runner` fixture. Reserve
`subprocess.run` for one packaging test asserting the installed console script exists and runs.

```python
def test_status_reports_json(cli_runner):
    code, out, err = cli_runner("status", "--json")
    assert code == 0
    assert json.loads(out)["state"] == "ready"
    assert err == ""
```

**Why**: In-process tests are fast, debuggable, and measure the code. Subprocess tests measure the
installed environment, which is a different and much smaller question.

---

# FEATURE: Init and Count

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | The `ledger init` command that empties the ledger and the `ledger count` command that reports table row counts. |
| Depends On | FEATURE-CliEntry.md, DATABASE.md, ARCHITECTURE.md |
| Provides | ledger init, ledger count |

## Purpose

`init` prepares an empty ledger for loading and use. `count` reports how many rows each table holds. Both are registered in `cli/commands/maintenance.py` through its `COMMANDS` mapping, with keys `("init",)` and `("count",)`, each taking no arguments.

## Behavior

### `ledger init`

- Opens the database through the entry point; opening creates the database file and declared schema when they do not yet exist.
- Removes every row from `transactions`, then `categories`, then `accounts` (foreign-key order).
- Returns no rows, so nothing is written to stdout, and exits `0`.
- Running it again on an empty ledger also exits `0`.

### `ledger count`

- Output is CSV: header `table,rows`, then the rows `accounts`, `categories`, `transactions` in that order, each with the number of rows stored, read from the database.
- Counts are never embedded; they are computed from the repository `list` results.

An argument given to either command is a usage error (exit 2).

## Database Interface

- `FEATURE-ACCOUNT-005` — read: list accounts to count them - supplies: — - returns: `account`
- `FEATURE-CATEGORY-005` — read: list categories to count them - supplies: — - returns: `category`
- `FEATURE-TXN-005` — read: list transactions to count them - supplies: — - returns: `txn_id`
- `FEATURE-TXN-006` — write: remove every transaction on init - supplies: `min_txn_id` - returns: —
- `FEATURE-CATEGORY-006` — write: remove every category on init - supplies: `min_category` - returns: —
- `FEATURE-ACCOUNT-006` — write: remove every account on init - supplies: `min_account` - returns: —

# FEATURE: Load CSV Reader

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Shared reader that opens a CSV file named on the command line, checks its header, and returns numbered rows. |
| Depends On | ARCHITECTURE.md, FEATURE-CliEntry.md |
| Provides | ledger_core.csvio |
| Consumes | ledger, cli.registry |

## Purpose

The three `ledger load <table> <csv>` commands share one reader so that file handling, header
checking, and the exit codes for unreadable files and malformed rows are identical. The reader
only reads: it never touches the database and never writes.

## Interface

`ledger_core.csvio.read_rows(path, header)`

- `path` is the file path named on the command line; `header` is the sequence of column names the
  table requires, in order.
- Returns a list of `(line_number, fields)` tuples, one per data row, in file order. `line_number`
  is the 1-based line of the file (the header is line 1, so the first data row is line 2). `fields`
  is a list of strings exactly as parsed by the `csv` module.
- A file that is missing or cannot be read or decoded raises `Operational` (exit 1).
- A header that differs from `header` in names or order, an empty file, or a data row whose field
  count differs from `len(header)` raises `Rejected` (exit 3), with a diagnostic naming the line.
- A file with a valid header and no data rows returns an empty list.
- Blank lines are not data rows and are skipped.

## Database Interface

- None — persistence is owned by DATABASE.md.

## Programmatic Acceptance

# FEATURE: Account Add

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Implements `ledger account add <code> <name>` and the shared `account_row` helper. |
| Depends On | FEATURE-CliEntry.md, FEATURE-Validation.md, DATABASE.md |
| Provides | ledger account add, ledger_core.accounts |
| Consumes | ledger_core.validation, ledger_core.money, cli.registry |

## Purpose

Create one account and print its row. The module `ledger_core.accounts` also exports the helper the
other account commands use to build an account row from live data.

## Behavior

1. `ledger account add <code> <name>` takes exactly two arguments; other counts exit 2.
2. Validate the code (1 to 12 characters of `A-Z0-9`) and the name (1 to 40 characters, no comma or
   newline). A violation exits 3.
3. A code that is already stored exits 3 and leaves the stored account unchanged.
4. Insert the account, then print CSV: the header `account,name,transactions,balance` and one row
   with the new account, its name, `0` transactions, and balance `0.00`.
5. A failing command writes nothing to standard output.

## Interface

`ledger_core.accounts.account_row(db, code)` returns `None` when the account is absent, otherwise
the tuple `(account, name, transactions, balance_cents)` where `transactions` is the number of that
account's stored transactions and `balance_cents` is the integer sum of their amounts. Both are
computed from the database on every call. Formatting the balance as text is done by
`ledger_core.money.format_cents` in the command, not in the helper.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: get an account by code - supplies: `account` - returns: `account`, `name`
- `FEATURE-ACCOUNT-001` — write: create an account - supplies: `account`, `name` - returns: `account`, `name`
- `FEATURE-TXN-005` — read: list an account's transactions to count and sum them - supplies: `account` - returns: `amount`

# FEATURE: Transaction Post

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Implements `ledger txn post`, validating every input and the balance rule before inserting one transaction. |
| Depends On | FEATURE-CliEntry.md, FEATURE-Validation.md, FEATURE-BalanceRule.md, DATABASE.md |
| Provides | ledger txn post, ledger_core.transactions |
| Consumes | ledger_core.validation, ledger_core.money, ledger_core.balances, cli.registry |

## Purpose

`ledger txn post <account> <category> <amount> <date> [<memo>]` records one transaction and prints the header row `txn_id,date,account,category,amount,memo` followed by the new row. `ledger_core.transactions` exports `txn_row` (formats a stored transaction as an output row) and `next_txn_id` (largest stored `txn_id` plus one, or 1 in an empty table), used by the other transaction commands and by transfer.

## Behavior

- Four or five arguments are required; otherwise exit 2. An omitted memo is stored as the empty string.
- Everything is checked before the write, in this order: amount, date, and memo validation; account exists; category exists; no resulting balance below zero. Any violation exits 3 and writes nothing.
- The amount is parsed to integer cents with no floating point and printed with exactly two decimals.
- The new `txn_id` is the largest present plus one, or 1 when none exist.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: check the account exists - supplies: `account` - returns: `account`
- `FEATURE-CATEGORY-002` — read: check the category exists - supplies: `category` - returns: `category`
- `FEATURE-TXN-005` — read: list transactions for balance and next id - supplies: `account` - returns: `txn_id`, `amount`
- `FEATURE-TXN-001` — write: create the transaction - supplies: `txn_id`, `date`, `account`, `category`, `amount`, `memo` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
