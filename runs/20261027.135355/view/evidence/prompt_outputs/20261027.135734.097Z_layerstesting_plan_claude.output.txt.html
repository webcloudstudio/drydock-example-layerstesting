# ARCHITECTURE: LayersTesting

## Questions

- None.

## Purpose

The product is an executable named `ledger` at the application root. It keeps accounts, categories, and cash transactions in SQLite through the generated `persistence` package. Every command either completes in full or changes nothing. This file states the module layout and boundaries every other Blueprint builds into.

Derived from `TECHNOLOGY_STACK.md`, which remains the decision of record.

| Technology | Where it applies |
|---|---|
| Python 3.11+ | All application code, the `ledger` launcher target, and the tests. |
| SQLite | The only store, reached through the generated `persistence` package. |
| CLI | The `ledger` executable and the `cli` package. |
| pytest | Test runner behind `bin/test.sh`. |
| POSIX sh | `bin/test.sh` and the `ledger` launcher. |

## Module Ownership

| Boundary | Owning module | May access |
|---|---|---|
| Persistence | `persistence` (generated) | The SQLite driver, the only module that does. |
| Configuration | `ledger_core.config` | `DATABASE_URL`, `DATABASE_PATH`, process environment. |
| Domain errors | `ledger_core.errors` | Nothing external. |
| Money and validation | `ledger_core.money`, `ledger_core.validation` | Nothing external; pure functions. |
| Command dispatch and output | `cli` | stdout, stderr, `ledger_core`, `persistence.open_database`. |
| File stores | none | The only files read are CSV files named on a command line, through `ledger_core.csvio`. |
| External services | none | No network access. |

No module outside `persistence` imports `sqlite3` or any other database driver. Callers use `db.<table>.<operation>(...)`.

## Configuration

`ledger_core.config.database_path() -> str` resolves `DATABASE_URL` first, with an optional leading `sqlite://` removed, then `DATABASE_PATH`, then `data/app.db`. An unset or empty value is skipped. A database location that cannot be opened is an operational failure: exit `1`, nothing written.

## Errors and Exit Codes

`ledger_core.errors` defines `LedgerError` with an integer `exit_code` attribute and three subclasses.

| Class | exit_code | Meaning |
|---|---|---|
| `Rejected` | 3 | Invalid input, duplicate key, unknown reference, account in use, negative balance. |
| `NotFound` | 4 | Absent account or transaction on get, rename, delete, or amend. |
| `Operational` | 1 | Unreadable file or unopenable database. |

Usage errors (exit `2`) are produced by `cli` dispatch and are not domain errors.

## Money

Amounts are integer cents at every layer: parsing, storage, arithmetic, and reports. Floating point is never used for money. Text is produced only at output by `ledger_core.money.format_cents`.

## Atomicity

Every writing command validates all inputs and rules, including the no-negative-balance rule, before its first write. A rejected command writes nothing.

## Test Command

`sh bin/test.sh` runs `pytest -q` and is the verification command for every behavioral story.

# FEATURE: CLI Entry

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | The `ledger` executable, command registry, dispatch rules, and stdout/stderr/exit-code contract. |
| Depends On | ARCHITECTURE.md, DATABASE.md |
| Provides | ledger, cli.registry |
| Consumes | persistence.accounts, persistence.categories, persistence.transactions |

## Questions

- None.

## Purpose

Provide the single entry point through which every command runs. It resolves the command words, checks the argument count, opens the database, calls the handler, and turns the result into CSV on stdout or one diagnostic line on stderr with the contract exit code.

## Interface

- `ledger` at the application root: a POSIX launcher that activates `.venv` and calls `cli.main(sys.argv[1:])`, exiting with its return value.
- `cli.main(argv: list[str] | None = None) -> int`.
- `cli.testing.cli_runner(*args) -> (exit_code, stdout, stderr)`, running `main` in process.
- `cli.registry`:
  - `Command(handler, min_args, max_args)`, a named tuple. `max_args` is `None` when unbounded.
  - `COMMANDS: dict[tuple[str, ...], Command]`, keyed by command words such as `("account", "add")`.
  - `load()`, idempotent: imports every module in `cli/commands/` and adds the entries of each module's `COMMANDS` mapping. It never removes entries.
- Handler signature: `handler(db, args: list[str]) -> list[list[str]]`, where `db` is the opened database and `args` are the words after the command words. It returns every output row, header first, as lists of text.

## Dispatch Rules

1. Call `registry.load()`.
2. Match the longest command-word prefix of `argv` in `COMMANDS`. No match, an empty `argv`, or a known group word with an unknown sub-word (unknown table or report) is a usage error.
3. An argument count outside `min_args..max_args` is a usage error.
4. A usage error exits `2`, writes one diagnostic line to stderr, and writes nothing to stdout.
5. Open the database with `persistence.open_database(ledger_core.config.database_path())`. A failure to open exits `1`.
6. Call the handler. On success, write the rows to stdout as CSV: comma-separated, no quoting, no trailing spaces, `\n` line endings. Nothing is written to stdout before the handler returns.
7. A `LedgerError` exits with its `exit_code` and one stderr line. Any other exception exits `1` with one stderr line. Stdout stays empty in both cases.

Handlers validate every input and rule before their first write. Check order inside a handler: input validation (exit 3), then existence lookups (exit 4), then business rules (exit 3).

## Database Interface

- None — persistence is owned by DATABASE.md; this entry point only opens the database and passes it to handlers.

# FEATURE: Validation

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Pure validation of codes, names, memos, amounts, and dates, and conversion between integer cents and two-decimal text. |
| Depends On | ARCHITECTURE.md |
| Provides | ledger_core.validation, ledger_core.money |

## Questions

- None.

## Purpose

Every command validates its inputs with these functions before it writes. They touch no storage and print nothing. Every violation raises `ledger_core.errors.Rejected` (exit code 3).

## Interface

`ledger_core.validation`, each returning the validated string unchanged:

| Function | Rule |
|---|---|
| `validate_code(value)` | 1 to 12 characters, each in `A-Z` or `0-9`. |
| `validate_name(value)` | 1 to 40 characters, no comma, no newline. Used for account names and category descriptions. |
| `validate_memo(value)` | 0 to 60 characters, no comma, no newline. |
| `validate_date(value)` | A real calendar date written `YYYY-MM-DD` with four-digit year, two-digit month and day. `2026-02-30` is rejected. |

`ledger_core.money`:

| Function | Rule |
|---|---|
| `parse_amount(text) -> int` | Input matches `-?DIGITS[.D[D]]`: at least one digit, an optional single decimal part of one or two digits, no sign other than `-`, no spaces. Returns integer cents. Zero (`0`, `0.00`, `-0`) is rejected. Three or more decimals are rejected. No floating point is used. |
| `format_cents(cents) -> str` | Exactly two decimal places, a leading `-` when negative, no thousands separator: `-12.50`, `0.00`, `5000.00`. |

## Database Interface

- None — this feature is pure and reaches no repository.

# FEATURE: Balance Rule

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Checks that a proposed set of transaction changes leaves no account balance below zero before anything is written. |
| Depends On | ARCHITECTURE.md, DATABASE.md |
| Provides | ledger_core.balances |
| Consumes | persistence.transactions |

## Questions

- None.

## Purpose

An account's balance is the sum of its transaction amounts in integer cents. Load, post, amend, delete, and transfer call this module before their first write. It only reads and never writes.

## Interface

`ledger_core.balances`:

| Name | Meaning |
|---|---|
| `Insert(account, amount)` | A transaction to be added to `account` with `amount` cents. |
| `Edit(txn_id, amount)` | A stored transaction whose amount becomes `amount`. |
| `Delete(txn_id)` | A stored transaction to be removed. |
| `current_balance(db, account) -> int` | Sum of the stored amounts of `account`; `0` when it has none. |
| `check_no_negative(db, changes)` | Raises `Rejected` (exit 3) if any affected account's resulting balance is below zero; returns `None` otherwise. |

`check_no_negative` groups all changes by account, takes each account's stored balance, applies the combined net delta (an `Edit` contributes new minus stored amount, a `Delete` contributes minus the stored amount), and rejects when any result is below zero. Changes are judged together, not one after another, so the order of changes does not matter. A resulting balance of exactly zero is allowed.

## Database Interface

- `FEATURE-TXN-002` — read: get a stored transaction for an edit or delete - supplies: `txn_id` - returns: `account`, `amount`
- `FEATURE-TXN-005` — read: list an account's transactions to sum its balance - supplies: — - returns: `amount`

# FEATURE: Init and Count

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | The `ledger init` command that empties the ledger and the `ledger count` command that reports table row counts. |
| Depends On | FEATURE-CliEntry.md, DATABASE.md, ARCHITECTURE.md |
| Provides | ledger init, ledger count |
| Consumes | ledger, cli.registry |

## Questions

- None.

## Purpose

`init` prepares an empty ledger for loading and use. `count` reports how many rows each table holds. Both are registered in `cli/commands/maintenance.py` through its `COMMANDS` mapping, with keys `("init",)` and `("count",)`, each taking no arguments.

## Behavior

### `ledger init`

- Opens the database through the entry point; opening creates the database file and declared schema when they do not yet exist.
- Removes every row from `transactions`, then `categories`, then `accounts` (foreign-key order).
- Returns no rows, so nothing is written to stdout, and exits `0`.
- Running it again on an empty ledger also exits `0`.

### `ledger count`

- Output is CSV: header `table,rows`, then the rows `accounts`, `categories`, `transactions` in that order, each with the number of rows stored, read from the database.
- Counts are never embedded; they are computed from the repository `list` results.

An argument given to either command is a usage error (exit 2).

## Database Interface

- `FEATURE-ACCOUNT-005` — read: list accounts to count them - supplies: — - returns: `account`
- `FEATURE-CATEGORY-005` — read: list categories to count them - supplies: — - returns: `category`
- `FEATURE-TXN-005` — read: list transactions to count them - supplies: — - returns: `txn_id`
- `FEATURE-TXN-006` — write: remove every transaction on init - supplies: `min_txn_id` - returns: —
- `FEATURE-CATEGORY-006` — write: remove every category on init - supplies: `min_category` - returns: —
- `FEATURE-ACCOUNT-006` — write: remove every account on init - supplies: `min_account` - returns: —
