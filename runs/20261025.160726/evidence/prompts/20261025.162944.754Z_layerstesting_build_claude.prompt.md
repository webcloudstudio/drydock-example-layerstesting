# Persistence & Service Encapsulation

**Type:** guidance
**Version:** 20261023 V5
**Category:** Persistence
**Description:** The single boundary rule for all persistent stores and external services — typed access classes, no raw access in application code

Technology reference. Framework-agnostic. This file does not change between projects.

Prerequisite: `stack/common.md`

---

## The Invariant

**Rule**: All persistence and external-service access goes through a typed encapsulation
class. Route, feature, and business-logic code never executes raw SQL, reads `os.environ`,
opens application files directly, or imports a cloud SDK (`boto3`). The typed class interface
— not the underlying schema or service — is the dependency boundary.

**Why**: A storage or service change is absorbed at the class. Downstream code depends on the
interface, so a schema change that does not change the interface changes nothing else. This is
the same swap-layer discipline a cloud client library enforces for AWS (`import boto3`
outside the wrapper fails review), generalized to every store.

A code review that finds raw SQL, `os.environ`, `open()` on application data, or a cloud SDK
import outside its encapsulation class fails.

**Relational rule**: the relational layer is generated, not written. Drydock emits it from
`DATABASE.md` and copies the engines in unchanged; the build writes callers. See section 1.

---

## 1. Relational stores → the generated persistence package

**You do not write this layer.** Drydock generates it from `DATABASE.md` at the DATABASE build
step and copies the engines in unchanged. Writing a repository, a connection helper, a session
factory, or a migration by hand is a review failure: the generated package already implements the
declaration, and a hand-written second path is storage access no Blueprint cites.

The build writes **callers**.

```text
route → service → db.<table>.<name>(...) → generated package → database
```

Language bindings are shipped in `languages/<language>/persistence/`; generation templates live
beside them in `templates/`. Python and Go implement the same declared operations. The language
instructions own native names, dependencies and fixtures. Go uses `OpenDatabase(ctx, dsn)` and
generated typed repository methods; the Python examples below use `open_database(dsn)`.

The Python package lands at `persistence/` in the build:

| File | Origin |
|---|---|
| `db.py`, `sqlite.py`, `postgres.py` | shipped by Drydock, copied unchanged |
| `schema.py` | generated from `DATABASE.md` — tables, operations, row dataclasses |
| `schema.sql` (beside the package) | generated DDL, applied once at the DATABASE step |

### Calling it

```python
from persistence import open_database

db = open_database(config.database_url)

ticket = db.tickets.get(id=ticket_id)                 # a frozen dataclass, or None
open_tickets = db.tickets.list(status="open")         # a list of them
history = db.rates.history(currency="USD", start_date=start)  # range list; end_date omitted
ticket = db.tickets.create(status="open", title=title)  # the declared Output row
db.tickets.update(id=ticket_id, status="closed")      # the row, or None
rate = db.rates.replace_rate(date=day, currency="USD", rate="1.0393")  # upsert: the row
changed = db.rates.reprice_currency(currency="USD", rate="1.0400")     # many-row update: a count
db.tickets.delete(id=ticket_id)                       # the Output built from the Match, or None
```

One attribute per declared table, one method per declared operation. The method name is the
`<name>` of the pattern's `Repository operation` cell, `<table>.<name>`, and its keyword arguments
are that pattern's `Input:` fields — nothing else is accepted. An operation the table does not
declare raises `UnknownOperation` naming what it does grant.

### Operations: a name and a Kind

An operation's **name** is the contract callers depend on. Its **Kind** is how the package runs
it, one of six: `get`, `list`, `create`, `update`, `upsert`, `delete`.

- **Simple:** the name is the Kind. `rates.get`, `rates.update` — no Kind row is written.
- **Named:** any other name declares its Kind: `rates.reprice_currency` with `| Kind | update |`.
  A table may hold several operations of one Kind, each under its own name. Two names with the
  same Kind, Match, Sets, and Output are synonyms, and the plan refuses the second.

**Which rows an operation reaches is declared, never inferred.** A pattern's `| Match |` row names
the Input fields that select rows, joined with AND, every field required except on a `list`. A
bare field is compared by equality with the column of its name; a term `<column> <op> <field>`
(`=`, `<`, `<=`, `>`, `>=`) compares an argument with a column, as `date >= start_date`. A Match
whose equality fields cover the table's `PK` or a declared `UNIQUE` reaches at most one row; any
other Match reaches many. A `list` with `| Order | `date` asc |` returns its rows in that order,
and in no stated order otherwise; do not re-sort or filter what an operation already returns. Every write is one statement inside the package, so a caller never composes a
read-then-write.

| Kind | Selects rows by | Writes | Rows | Returns |
|---|---|---|---|---|
| `get` | Match: a unique key | — | 0..1 | the row, or `None` |
| `list` | each supplied Input field, compared as its Match term states (optional filters) | — | 0..n | a list of rows, in its Order |
| `create` | — | every Input field | 1 | the row |
| `update` | Match (default: the `PK`); comparison terms allowed | the other Input fields supplied | 0..1 on a unique key, else 0..n | the row or `None`; the count when it reaches many |
| `upsert` | Match: exactly one unique key | inserts the row, or replaces its other Input fields | 1 | the row |
| `delete` | Match: every Input field; comparison terms allowed | — | 0..1 on a unique key, else 0..n | the Output built from the Match or `None`; the count when it reaches many |

No other operator, no OR, no join, and no SQL exists outside the package.

### The operation contract

`DATABASE_compact.md` ends with a generated `## Operation Surface`: per table, one block per
operation, rendered from the declaration by Drydock, never by a model. Build against it.

````markdown
#### `db.rates.replace_rate` — FEATURE-RATE-004

| Kind | Rows | Match | Sets | Contract |
|---|---|---|---|---|
| upsert | 1 | `date`, `currency` | `rate` | `3f9a1c04be72` |

- Input: `{"date": "str", "currency": "str", "rate": "str"}`
- Output: `{"id": "int", "date": "str", "currency": "str", "rate": "str"}`

```sql
INSERT INTO "rates" ("date", "currency", "rate") VALUES (?, ?, ?) ON CONFLICT ("date", "currency") DO UPDATE SET "rate" = excluded."rate";
SELECT "id", "date", "currency", "rate" FROM "rates" WHERE "date" = ? AND "currency" = ?;
```
````

- **Call:** `db.<table>.<name>(...)`; Go `db.<Table>.<Name>(ctx, <Table><Name>Input{...})`.
- **Input / Output:** JSON field names with caller types `str`, `int`, `float`, `bool`, `bytes`.
  `?` marks a field the caller may omit: a `list` filter or bound, or a column an `update` sets
  only when supplied. A `- Order:` line states a `list`'s sort keys. Output is `{...}`, `{...} | null`, `[{...}]`, or `"int" (rows changed)`.
- **SQL:** the statements the runtime executes, in SQLite placeholder form; PostgreSQL binds the
  same positions. A test holds it byte-identical to the shipped driver.
- **Contract:** the operation's fingerprint, the first 12 hex digits of a SHA-256.

### What forces a rebuild

Only a contract change. The fingerprint hashes the name, Kind, Match terms, Order, rows, return shape, and each
Input and Output field's name and caller type. It excludes everything a caller cannot see: column
length (`VARCHAR(12)` and `VARCHAR(40)` are both `str`), nullability, `Required`, `DEFAULT`,
indexes, and the SQL. Refit rebuilds the callers of an operation only when its fingerprint moves;
any other `DATABASE.md` edit rebuilds the generated package alone.

**The declaration fixes the surface.** `DATABASE.md` names every operation in the
`Repository operation` cell of each access pattern, as `<table>.<name>`. That is the persistence
surface, not a suggestion for one. To reach the store differently, change the declaration and
rebuild; there is no second door.

**Why**: the declaration is the only description of the store the rest of the plan is allowed to
depend on. Generating from it means the operations a Blueprint cites and the operations that exist
cannot drift — they are the same list. Plan already refuses to write a plan whose tables,
operations, and citations disagree; generating the layer keeps the built code in that agreement
rather than trusting each build to re-derive it from prose.

**Caller contract**: `Database` presents single-threaded semantics. Callers construct one instance,
share it freely, call methods synchronously, and never reason about threads, connections, or
locking. Connection lifetime is internal to the package and may change without affecting any
caller. Returned rows are frozen dataclasses and carry no connection state.

**Engine selection is runtime, not build time.** Both engines are copied into every build and
chosen from the DSN, because the same build runs SQLite in development and test and PostgreSQL in
production. `VARCHAR(n)` is declared once and emitted to both: PostgreSQL enforces the length,
SQLite parses the same declaration and ignores it.

**Schema is built once.** `schema.sql` is applied at the DATABASE build step and never again
within a release. Application startup does not create or alter schema.

**Guardrails**

- Do not write a repository, DAO, ORM model, or session factory.
- Do not import `sqlite3`, `psycopg`, or a SQL string anywhere outside `persistence/`.
- Do not edit anything under `persistence/` — edit `DATABASE.md` and rebuild.
- Do not create or alter schema at application startup.

### Acceptance transactions

**Acceptance store lifecycle.** The DATABASE step provisions and verifies the configured store
once. Criteria never replace DATABASE_URL/DATABASE_PATH, create a temporary database, apply DDL,
or assume an empty store. The store may hold data before any criterion runs: assert on records the
criterion created, or on a count read before setup (`after == before + 5`), never on an absolute
table count.

The acceptance harness owns isolation. It begins one transaction before each Python criterion and
rolls it back when the criterion ends, pass or fail. Every database the criterion's process opens
joins it: `db_session()`, the application behind `web_client()`, and commands run through
`cli_runner()`. Setup, behavior and readback therefore see one another's writes, and none persists;
leaving a `with db_session() as db:` block rolls nothing back. Seed with `with db_session() as db:`
and pass that database into feature operations. Never commit, clean up, or open a transaction.

A criterion that launches a process (`subprocess`, a server on a port, a shell script) cannot see
that transaction. It does not open the store and does not depend on rows it wrote; exercise stored
behavior in-process instead. Go criteria use `OpenSession(ctx, "")` with checked deferred cleanup,
which rolls back its own transaction. Go HTTP, CLI and restart criteria use
`OpenCommittedSession(ctx, "")` with a criterion-owned identifier and checked `defer` cleanup
through supported product interfaces. Database acceptance must not be replaced by a project test
count: runtime catalog and row-count evidence proves provisioning, feature criteria prove behavior.

## 2. Config / `.env` → one typed Config class

One typed `Config` reads the environment once and validates at startup. Nothing else reads
`os.environ`. There are no `Dev`/`Prod`/`Test` subclasses — every field is inherited from the
environment, so the environment (`.env`) selects the configuration, not a Python subclass.

```python
# config.py
import os
from dataclasses import dataclass
from dotenv import load_dotenv
load_dotenv()

@dataclass(frozen=True)
class Config:
    secret_key: str
    database_path: str
    port: int
    debug: bool = False

    @classmethod
    def load(cls) -> "Config":
        try:
            return cls(
                secret_key=os.environ["SECRET_KEY"],
                database_path=os.environ.get("DATABASE_PATH", "data/app.db"),
                port=int(os.environ.get("APP_PORT", "5001")),
                debug=os.environ.get("APP_DEBUG") == "1",
            )
        except KeyError as e:
            raise RuntimeError(f"Missing required env var: {e}") from e
```

Typed fields mean a missing or malformed variable crashes at startup, not at first use.

## 3. Files → typed FileStore class

A `FileStore` owns a root directory and is the only code that opens application files. Callers
never build paths or call `open()`/`shutil` directly.

```python
# filestore.py
from pathlib import Path

class FileStore:
    def __init__(self, root: str): self._root = Path(root)
    def read(self, name: str) -> str:
        return (self._root / name).read_text(encoding="utf-8")
    def write(self, name: str, data: str) -> None:
        p = self._root / name; p.parent.mkdir(parents=True, exist_ok=True)
        p.write_text(data, encoding="utf-8")
    def list(self, pattern: str = "*") -> list[str]:
        return [p.name for p in self._root.glob(pattern)]
```

Path-traversal validation and atomic writes live here, once.

## 4. External services → wrapper modules over a shared base class

Every external-service wrapper extends one `ServiceClient` base class. The base owns the
backend handle, a named logger, and a uniform call guard; subclasses expose typed methods and
never leak the SDK client.

```python
# service.py — base class for all external-service wrappers
import logging

class ServiceClient:
    """Base for service wrappers. Owns the backend handle, logger, and a uniform
    call guard. Subclasses expose typed methods; they never expose the SDK client."""
    def __init__(self, backend, name: str | None = None):
        self._backend = backend
        self.log = logging.getLogger(name or type(self).__name__)

    def _guard(self, op, *args, **kwargs):
        try:
            return op(*args, **kwargs)
        except Exception:
            self.log.exception("%s call failed", type(self).__name__)
            raise
```

Wrappers subclass it. AWS commonly uses a project-owned cloud client library
(`client.queue`, `client.share`, `client.catalog`); any new service follows the same shape — e.g.
a `MessageBus` over SQS, even when it maps 1:1:

```python
# messagebus.py — the wrapper hides the transport
class MessageBus(ServiceClient):
    def publish(self, topic: str, payload: dict) -> str:
        return self._guard(self._backend.send, topic, payload)
    def subscribe(self, topic: str, handler) -> None: ...
```

**Why**: the base class makes logging and error handling uniform across services; the wrapper
is the seam. Swapping the transport, or stubbing it in tests, changes one class. See
`stack/cloud-client-library.md`, `stack/aws-sqs.md`, `stack/aws-s3.md`, `stack/aws-dynamodb.md`.

| `get` | the Output row, or `None` (Go `nil`) when nothing matches |
| `list` | a list of Output rows, one per record; the Output names the row's columns |
| `create` | the Output row, read back by key; the key when no Output is declared |
| `update` | the Output row, read back by its Match, or `None` when nothing matched; the count when it reaches many rows or no Output is declared |
| `upsert` | the Output row inserted or replaced, read back by its Match |
| `delete` | the Output built from its Match, or `None` when nothing matched; the count when it reaches many rows or no Output is declared |

`db_session()` opens the configured application store (DATABASE_URL, else DATABASE_PATH,
else data/app.db). Schema is provisioned only at the DATABASE step. Pass the yielded database into
the feature. Under the acceptance harness, every database the criterion's process opens, including
this fixture, the application behind `web_client()`, and commands run through `cli_runner()`, joins
one transaction that the harness rolls back when the criterion ends, pass or fail. Leaving the
`with` block rolls nothing back, so a later request still sees the setup. Outside the harness (the
project's pytest suite) the fixture starts its own transaction and rolls it back on exit. It never
creates a temporary database or applies schema. `committed_session()` opens the same store with
autocommit for project tests that need committed state, and joins the harness transaction under
acceptance. A process the criterion launches cannot see that transaction and must not depend on
its rows. Never reset the database or delete unrelated records.

## You do not write the access layer

Drydock generates the persistence package from `DATABASE.md` and copies the SQLite engine in
unchanged. Connection handling, thread discipline, PRAGMAs, parameter binding, and row mapping all
live there. A hand-written connection helper, cursor, or SQL string is a review failure.

**By language**

| Language | Adapter | What the build writes |
|---|---|---|
| Python | `Rigging/languages/python/persistence/sqlite.py`, shipped | callers only — `db.<table>.<verb>(...)` |
| Go | `Rigging/languages/go/persistence/sqlite.go`, shipped | typed callers; declarations and fixtures are generated |
| other languages | none yet | a Target declaring `DATABASE.md` fails before planning |

## Role

SQLite is the development and test engine. It is a file, it needs no server, and it opens from a
plain path or a `sqlite://` DSN. Production relational storage is PostgreSQL; see
`stack/postgres.md`.

Both engines are copied into every build and selected at runtime from the DSN, so the same build
runs SQLite in test and PostgreSQL in production without rebuilding.

## What it enforces

`PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `DEFAULT`, and — with `PRAGMA foreign_keys=ON`, which the
shipped engine sets — `REFERENCES`.

## What it ignores

**Column length.** SQLite has type affinity, not length. `VARCHAR(50)` parses and is stored as
`TEXT`, and a 500-character value is accepted. The same declaration is emitted to PostgreSQL,
which does enforce it, so **a length violation passes in test and fails in production.** Declare
lengths for the production engine and do not rely on SQLite to catch them.

**Type strictness.** Any value may be stored in any column. A test that passes on SQLite has not
proven the column types.

**`ALTER TABLE`.** Only `ADD COLUMN` and `RENAME` are supported; there is no `DROP COLUMN` before
3.35, no type change, and no `ADD CONSTRAINT`. Within a release this never arises — the schema is
built once, at the DATABASE build step, from `schema.sql`.

## Guardrails

- Never import `sqlite3` outside the generated `persistence/` package.
- Never hold a `sqlite3.Connection` on an application object; the engine owns connection lifetime.
- Never create or alter schema at application startup.
- Never treat a green SQLite test as proof that column lengths or types hold in production.

## Foundation Contract

The published shape of this foundation. Drydock synthesizes the story that builds it and every

- package: cli
- entry: main(argv: list[str] | None = None) -> int

```python
# cli/__init__.py
def main(argv: list[str] | None = None) -> int:
    ...

# cli/testing.py
import contextlib
import io
from cli import main

def cli_runner(*args: str) -> tuple[int, str, str]:
    """Return (exit_code, stdout, stderr) without spawning a process."""
    out, err = io.StringIO(), io.StringIO()
    with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
        code = main(list(args))
    return code, out.getvalue(), err.getvalue()

# conftest.py
import pytest
from cli import testing

@pytest.fixture
def cli_runner():
    return testing.cli_runner
```

A criterion imports `cli_runner` from `cli.testing`, calls `cli_runner("status", "--json")`, and
asserts on the returned tuple. It does not call `subprocess.run`, which measures the installed
console script and the shell rather than the code the story wrote.

---

## 1. Directory Layout

**Rule**: Command code lives in `cli/`. The root holds only packaging and infrastructure files.

```
project/
  pyproject.toml            # [project.scripts] declares the console script
  cli/
    __init__.py             # main() — the single entry point
    commands.py             # one function per command; no argument parsing
    parser.py               # argparse construction; no behavior
  bin/
    run.sh                  # bash launcher
    run.ps1                 # PowerShell launcher
  tests/
```

**Why**: Parsing, behavior, and launching are three contracts. Collapsing them produces a command
that cannot be tested without a shell.

---

## 2. Entry Point and Exit Codes

**Rule**: `main(argv=None) -> int` parses, dispatches, and returns an exit code. It never calls
`sys.exit` and never raises for an expected failure. The console script is the only caller that
translates the return value into a process exit.

```python
# cli/__init__.py
import sys
from cli.parser import build_parser
from cli import commands

def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        return commands.dispatch(args)
    except OperationalError as exc:
        print(f"error: {exc}", file=sys.stderr)
        return 1
```

```toml
# pyproject.toml
[project.scripts]
mytool = "cli:main"
```

**Exit codes**: `0` success, `1` operational failure, `2` usage error. `argparse` already returns
`2` for a usage error; do not override it.

**Why**: A `main` that returns rather than exits is callable from a test in-process. A `main` that
calls `sys.exit` forces every criterion to spawn a subprocess and measure the shell.

---

## 3. Parsing Is Separate From Behavior

**Rule**: `parser.py` builds the `argparse` tree and returns it. `commands.py` holds one function
per command taking plain arguments, not a `Namespace`. Neither imports the other.

```python
# cli/parser.py
import argparse

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mytool")
    sub = parser.add_subparsers(dest="command", required=True)
    status = sub.add_parser("status", help="Report current state")
    status.add_argument("--json", action="store_true")
    return parser
```

```python
# cli/commands.py
def status(*, as_json: bool) -> int:
    ...

def dispatch(args) -> int:
    if args.command == "status":
        return status(as_json=args.json)
    return 2
```

**Why**: Behavior tested through a `Namespace` is behavior tested through the parser. Separating
them lets a criterion call `status(as_json=True)` directly.

---

## 4. Cross-Platform Launchers

**Rule**: Ship both launchers. They locate the environment and invoke the package entry point;
they contain no business logic. A launcher that makes a decision is a second implementation of the
command.

```bash
#!/usr/bin/env bash
# bin/run.sh — locate the environment and hand off. No business logic.
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
if [ -d "$ROOT/.venv" ]; then
    source "$ROOT/.venv/bin/activate"
fi
exec python -m cli "$@"
```

```powershell
# bin/run.ps1 — locate the environment and hand off. No business logic.
$ErrorActionPreference = "Stop"
$Root = Split-Path -Parent $PSScriptRoot
$Activate = Join-Path $Root ".venv\Scripts\Activate.ps1"
if (Test-Path $Activate) { & $Activate }
python -m cli @args
exit $LASTEXITCODE
```

```python
# cli/__main__.py — makes `python -m cli` work identically on both platforms
import sys
from cli import main

sys.exit(main())
```

**Why**: `python -m cli` is the one invocation both launchers share, so the two scripts cannot
drift in behavior — only in how they find the interpreter. `exit $LASTEXITCODE` is required in
PowerShell; without it the exit code is discarded and a failing command reports success.

---

## 5. Output and Streams

**Rule**: Results go to stdout, diagnostics to stderr. A `--json` mode prints one JSON document to
stdout and nothing else. Never interleave progress text into a machine-readable stream.

**Why**: A caller piping stdout to `jq` receives the progress lines too, and the command becomes
unusable in a pipeline.

---

## 6. Testing Without a Process

**Rule**: Test through `main(["status", "--json"])` or the `cli_runner` fixture. Reserve
`subprocess.run` for one packaging test asserting the installed console script exists and runs.

```python
def test_status_reports_json(cli_runner):
    code, out, err = cli_runner("status", "--json")
    assert code == 0
    assert json.loads(out)["state"] == "ready"
    assert err == ""
```

**Why**: In-process tests are fast, debuggable, and measure the code. Subprocess tests measure the
installed environment, which is a different and much smaller question.

## Command Flow

1. `main` parses `argv`, finds the longest registered command prefix, and checks argument count.
2. The handler checks every input and every rule, computes the full change, and only then writes.
3. The handler returns rows (a header row and data rows) or `None`.
4. `main` writes the rows to standard output as CSV only after the handler has returned.
5. A raised `LedgerError` becomes its exit code and one line on standard error; standard output stays empty.

## Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Success. |
| 1 | Operational failure: database unreachable, tables missing, file unreadable, or any unexpected exception. |
| 2 | Usage error: unknown command, table, or report; wrong argument count. |
| 3 | Rejected: invalid input, duplicate key, unknown reference, account in use, or a change that would leave a negative balance. |
| 4 | Not found: an absent account or transaction id. |

## Output Contract

Successful commands except `init` write CSV: one header row, then data rows, comma-separated, no
quoting, no trailing spaces, `\n` line endings. Amounts print with exactly two decimals, a leading
`-` when negative, and no thousands separator. Failures write nothing to standard output and one
diagnostic line to standard error.

## Guardrails on Design

- Report values, counts, and totals are always computed from database reads, never embedded.
- No floating point for money at any layer.
- Application code never reads `sources/run.sh` or any seed file; seed files reach the database only through `ledger load`.

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | The cli package entry point: command registry, dispatch, exit-code mapping, CSV output, diagnostics, and database location. |

## Purpose

Every command in the ledger plugs into one dispatcher. This story builds the dispatcher and registers no command. Later stories add modules under `cli/commands/` that call `register`. `main` imports every module in the `cli.commands` package (for example with `pkgutil.iter_modules`) before dispatching, so adding a command never edits `main`.

## Interface

| Symbol | Contract |
|--------|----------|
| `cli.main(argv=None) -> int` | Runs one command and returns its exit code. `None` means `sys.argv[1:]`. |
| `cli.registry.register(words, handler, nargs)` | `words` is a tuple such as `("account", "add")`. `handler(args: list[str])` returns a list of rows (each a list of strings) or `None`. `nargs` is `(min, max)` for the arguments after the words. |
| `cli.errors.LedgerError(message)` | Base class with an integer `code`. Subclasses: `OperationalError` 1, `UsageError` 2, `Rejected` 3, `NotFound` 4. |
| `cli.config.resolve_dsn(environ) -> str` | Returns `DATABASE_URL`, else `DATABASE_PATH`, else the absolute path of `data/app.db` under the application root. An empty value counts as unset. The value is returned as written; the persistence library selects the engine and strips an optional `sqlite://` prefix. |
| `cli.context.open_store()` | Calls `persistence.open_database(resolve_dsn(os.environ))`. For a SQLite file it creates a missing parent directory first. |
| `cli.testing.cli_runner(*args)` | Returns `(exit_code, stdout, stderr)` by calling `main` in process. |

## Dispatch Rules

- The longest registered word prefix of `argv` selects the handler. No match, or no arguments at all, is a usage error (exit 2).
- An argument count outside `nargs` is a usage error (exit 2) and the handler is not called.
- The handler runs to completion before anything is written to standard output. Rows are then written with `csv.writer` semantics but unquoted fields, `\n` line endings, and `sys.stdout` looked up at call time.
- A `LedgerError` becomes its `code`, one diagnostic line on standard error, and nothing on standard output.
- A `persistence.PersistenceError` and any other unexpected exception become exit 1 with one diagnostic line.
- Diagnostics are never part of any contract; only the exit code and standard output are.

- None — persistence is owned by DATABASE.md.

14. `FILES CHANGED` must list only files actually written in the build working
   directory. When the existing implementation already satisfies this step, report
   `RESULT: SUCCESS`, list no changed files, and state the checks performed and their results.
   A verification-only step requires no application changes. Drydock runs the declared
   deterministic checks and decides the outcome independently of this report.
15. On `RESULT: FAILED`, append two additional lines so the failure is actionable
   without opening logs. `FAILURE_SUMMARY` is one line naming the cause;
   `FAILURE_DETAIL` states what happened, why, and what to change before a rerun.
   Name concrete conditions when they apply: token or context limit exceeded,
   could not execute commands in this environment, a required input was missing,
   or a specific tool or command failed.

```text
FAILURE_SUMMARY: <one line naming the cause>
FAILURE_DETAIL: <what happened, why, and what to change before rerunning>
```

16. When a declared acceptance criterion cannot pass no matter how the code is written,
   say so with this exact token. You may not edit the criterion — it is staged and
   restored before grading:

```text
AC_BROKEN: <check-id>[, <check-id>]
```

   This is a report, not a verdict, and it stops nothing. A criterion reaches you only
   when its expected value is one its author could not have invented — a status code, a
   staged suite's exit status, a value the criterion itself supplied as input — so your
   claim that the criterion rather than the code is at fault is the less likely
   explanation, and the budget is spent as it would be for any other failure. A
   criterion whose expectation *was* hand-typed already settles `DISPUTED` on its own,
   without you naming it. Emit the token only after running the criterion and confirming
   the underlying command succeeded while the assertion still failed. Name the affected
   check ids, emit it alongside your normal `RESULT` line, state the reasoning in
   `FAILURE_DETAIL`, and emit it even when `RESULT: SUCCESS`. Do not use it for a
   criterion you merely failed to satisfy.
