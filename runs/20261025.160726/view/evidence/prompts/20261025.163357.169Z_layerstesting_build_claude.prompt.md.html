import contextlib
import io
from cli import main

def cli_runner(*args: str) -> tuple[int, str, str]:
    """Return (exit_code, stdout, stderr) without spawning a process."""
    out, err = io.StringIO(), io.StringIO()
    with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):

    return code, out.getvalue(), err.getvalue()

## 1. Directory Layout

**Rule**: Command code lives in `cli/`. The root holds only packaging and infrastructure files.

```
project/
  pyproject.toml            # [project.scripts] declares the console script
  cli/
    __init__.py             # main() — the single entry point
    commands.py             # one function per command; no argument parsing
    parser.py               # argparse construction; no behavior
  bin/
    run.sh                  # bash launcher
    run.ps1                 # PowerShell launcher
  tests/
```

**Why**: Parsing, behavior, and launching are three contracts. Collapsing them produces a command
that cannot be tested without a shell.

---

## 2. Entry Point and Exit Codes

**Rule**: `main(argv=None) -> int` parses, dispatches, and returns an exit code. It never calls
`sys.exit` and never raises for an expected failure. The console script is the only caller that
translates the return value into a process exit.

```python
# cli/__init__.py
import sys
from cli.parser import build_parser
from cli import commands

def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        return commands.dispatch(args)
    except OperationalError as exc:
        print(f"error: {exc}", file=sys.stderr)
        return 1
```

```toml
# pyproject.toml
[project.scripts]
mytool = "cli:main"
```

**Exit codes**: `0` success, `1` operational failure, `2` usage error. `argparse` already returns
`2` for a usage error; do not override it.

**Why**: A `main` that returns rather than exits is callable from a test in-process. A `main` that
calls `sys.exit` forces every criterion to spawn a subprocess and measure the shell.

---

## 3. Parsing Is Separate From Behavior

**Rule**: `parser.py` builds the `argparse` tree and returns it. `commands.py` holds one function
per command taking plain arguments, not a `Namespace`. Neither imports the other.

```python
# cli/parser.py
import argparse

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mytool")
    sub = parser.add_subparsers(dest="command", required=True)
    status = sub.add_parser("status", help="Report current state")
    status.add_argument("--json", action="store_true")
    return parser
```

```python
# cli/commands.py
def status(*, as_json: bool) -> int:
    ...

def dispatch(args) -> int:
    if args.command == "status":
        return status(as_json=args.json)
    return 2
```

**Why**: Behavior tested through a `Namespace` is behavior tested through the parser. Separating
them lets a criterion call `status(as_json=True)` directly.

---

## 4. Cross-Platform Launchers

**Rule**: Ship both launchers. They locate the environment and invoke the package entry point;
they contain no business logic. A launcher that makes a decision is a second implementation of the
command.

```bash
#!/usr/bin/env bash
# bin/run.sh — locate the environment and hand off. No business logic.
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
if [ -d "$ROOT/.venv" ]; then
    source "$ROOT/.venv/bin/activate"
fi
exec python -m cli "$@"
```

```powershell
# bin/run.ps1 — locate the environment and hand off. No business logic.
$ErrorActionPreference = "Stop"
$Root = Split-Path -Parent $PSScriptRoot
$Activate = Join-Path $Root ".venv\Scripts\Activate.ps1"
if (Test-Path $Activate) { & $Activate }
python -m cli @args
exit $LASTEXITCODE
```

```python
# cli/__main__.py — makes `python -m cli` work identically on both platforms
import sys
from cli import main

sys.exit(main())
```

**Why**: `python -m cli` is the one invocation both launchers share, so the two scripts cannot
drift in behavior — only in how they find the interpreter. `exit $LASTEXITCODE` is required in
PowerShell; without it the exit code is discarded and a failing command reports success.

---

## 5. Output and Streams

**Rule**: Results go to stdout, diagnostics to stderr. A `--json` mode prints one JSON document to
stdout and nothing else. Never interleave progress text into a machine-readable stream.

**Why**: A caller piping stdout to `jq` receives the progress lines too, and the command becomes
unusable in a pipeline.

---

## 6. Testing Without a Process

**Rule**: Test through `main(["status", "--json"])` or the `cli_runner` fixture. Reserve
`subprocess.run` for one packaging test asserting the installed console script exists and runs.

```python
def test_status_reports_json(cli_runner):
    code, out, err = cli_runner("status", "--json")
    assert code == 0
    assert json.loads(out)["state"] == "ready"
    assert err == ""
```

**Why**: In-process tests are fast, debuggable, and measure the code. Subprocess tests measure the
installed environment, which is a different and much smaller question.

# Persistence & Service Encapsulation — Contract Surface

## Relational Persistence

### Rule: persistence-boundary

All persistence and external-service access goes through typed encapsulation classes.

Constraints: Route, feature, and business-logic code must not execute raw SQL, read `os.environ`, open application files, import `sqlite3`/`psycopg`, or import cloud SDKs outside their encapsulation classes.

### function_open_database

Opens the generated persistence package using a database DSN.

| Parameter | Type |
|---|---|
| `dsn` | `str` |

Returns a `Database` instance with one attribute per declared table.

Constraints: Callers use the generated package and must not write repositories, DAOs, ORM models, connection helpers, session factories, or migrations.

### Database.<table>.<operation>

Executes a declared database operation using keyword arguments matching its `Input` fields.

| Input | Type |
|---|---|
| Declared operation fields | `str`, `int`, `float`, `bool`, or `bytes` |

Returns the declared operation `Output`: a row, `None`, a list of rows, or an integer row count.

Constraints: Unknown operations raise `UnknownOperation`. No other arguments, operators, OR conditions, joins, or SQL access paths are accepted. Calls are synchronous, and returned rows are frozen dataclasses without connection state.

### Rule: operation-kinds

Declared operations use one of six kinds: `get`, `list`, `create`, `update`, `upsert`, or `delete`.

Constraints: Operation names are the caller contract. Match fields select rows using AND semantics; bare fields use equality, and comparison terms may use `=`, `<`, `<=`, `>`, or `>=`. `list` filters are optional. `Order` controls list ordering. Every write executes as one package-level statement.

| Kind | Selection | Return |
|---|---|---|
| `get` | Unique-key match | Row or `None` |
| `list` | Optional input-field match | Ordered list of rows |
| `create` | None | Created row |
| `update` | Match, defaulting to primary key | Row/`None`, or count for many rows |
| `upsert` | Exactly one unique-key match | Inserted or replaced row |
| `delete` | Input-field match | Matched output/`None`, or count for many rows |

### Rule: operation-surface

Each operation exposes a generated contract containing its call path, kind, rows, match terms, sets, input schema, output schema, SQL, and 12-character SHA-256 contract fingerprint.

Constraints: Callers build against `DATABASE_compact.md`’s generated `Operation Surface`. Contract fingerprints change only when the operation name, kind, match, order, row behavior, return shape, or input/output field names and types change.

### Rule: database-runtime

The generated package supports SQLite and PostgreSQL selected from the runtime DSN.

Constraints: Both engines are present in every build. The schema is applied once during the DATABASE build step and is not created or altered at application startup.

# FEATURE: Init

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | The `ledger init` command that returns the three ledger tables to an empty state. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-CliEntry.md, FEATURE-LedgerCore.md |
| Provides | ledger init |
| Consumes | cli.registry.register, cli.context.open_store |

## Purpose

`ledger init` drops all three tables if present and recreates them empty, writing nothing to standard output. It takes no arguments; any argument is a usage error (exit 2) and changes nothing. This is the contract surfaced in the commands table of the source instructions.

## Behavior

1. Open the store with `cli.context.open_store()`.
2. Make sure the three tables exist. If opening a store that has no tables does not already create them, apply the generated idempotent `schema.sql` through the persistence library's own facility. Application code never executes driver calls itself. The grader runs `ledger init` against a brand-new database file, so this step must work on an empty store.
3. Empty the tables in foreign-key order with the declared clear operations: transactions first, then accounts, then categories.
4. Return `None` so standard output stays empty; exit 0.
5. An unreachable database exits 1.

The registration is `register(("init",), handler, (0, 0))` in `cli/commands/init.py`.

## Database Interface


- `FEATURE-ACCOUNT-006` — write: accounts.clear - supplies: `first_code` - returns: —
- `FEATURE-CATEGORY-004` — write: categories.clear - supplies: `first_code` - returns: —
- `FEATURE-TXN-006` — write: transactions.clear - supplies: `min_id` - returns: —

# FEATURE: Account Add

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Implements `ledger account add <code> <name>`, which creates one validated account. |

| Provides | ledger account add |
| Consumes | cli.main, format_amount, validate_code, validate_text |

## Purpose

Add a new place where the shop keeps cash. A new account has no transactions and a zero balance.

## Command Contract

`ledger account add <code> <name>` registers under the `account` command in the cli command table.

| Condition | Result |
|---|---|
| Valid code and name, code not in use | Exit 0. Stdout is `account,name,transactions,balance` then the new row with `0` transactions and balance `0.00`. |
| Wrong argument count | Exit 2, nothing on stdout. |
| Code not 1 to 12 characters of `A-Z0-9` | Exit 3, nothing stored. |
| Name empty, longer than 40 characters, or containing a comma or newline | Exit 3, nothing stored. |
| Code already exists | Exit 3, nothing stored. |

## Behavior

1. Validate the code and name with the `ledger-core` validators.
2. Confirm the code is not already stored.
3. Create the row, then print the account row. The transaction count and balance are computed from
   the database, never hard-coded, and formatted from integer cents with two decimal places.
4. A failing command writes one diagnostic line to standard error and nothing to standard output.

## Database Interface

- `FEATURE-ACCOUNT-003` — write: create an account - supplies: `account`, `name` - returns: `account`, `name`
- `FEATURE-ACCOUNT-002` — read: detect an existing code - supplies: `account` - returns: `account`, `name`
- `FEATURE-TXN-002` — read: count the account's transactions and sum its balance - supplies: `account` - returns: `txn_id`, `amount`

# FEATURE: Transaction Post

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Implements `ledger txn post`, recording one receipt or payment against an account in integer cents. |
| Depends On | FEATURE-AccountAdd.md, FEATURE-LoadCategories.md, FEATURE-LedgerCore.md, FEATURE-CliEntry.md, DATABASE.md |
| Provides | ledger txn post |
| Consumes | transactions.create, transactions.list, accounts.list, categories.get |

## Purpose

Post a single transaction. Every input and the non-negative balance rule are checked before the first
write, so a rejected post changes nothing.

## Command Contract

| Aspect | Rule |
|--------|------|
| Invocation | `ledger txn post <account> <category> <amount> <date> [<memo>]`: four or five arguments. |
| Amount | Matches `-?DIGITS[.D[D]]`, at most two decimals, never zero. Parsed to integer cents by the shared core; no floating point. |
| Date | A real calendar date written `YYYY-MM-DD`. |
| Memo | Optional, 0 to 60 characters, no comma or newline. Absent means the empty string. |
| Account and category | Both must exist; otherwise exit 3. |
| Transaction id | One more than the largest `txn_id` present, or `1` in an empty table. |
| Balance | If the account balance after the post would be below zero, exit 3 before any write. |
| Success stdout | Header `txn_id,date,account,category,amount,memo`, then the new row with the amount as two-decimal text. |
| Rejection | Exit 3, nothing on stdout, no row stored. |
| Wrong argument count | Exit 2, nothing on stdout. |

## Database Interface

- `FEATURE-TXN-003` — write: create a transaction - supplies: `txn_id`, `date`, `account`, `category`, `amount`, `memo` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TXN-002` — read: list transactions to find the largest id and the account balance - supplies: `account` - returns: `txn_id`, `amount`
- `FEATURE-ACCOUNT-002` — read: confirm the account exists - supplies: `account` - returns: `account`

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Specifies the input validation `ledger txn post` applies to category, amount, and date before it writes anything. |
| Depends On | FEATURE-TxnPost.md, FEATURE-LedgerCore.md, DATABASE.md |
| Provides | txn post validation |
| Consumes | ledger txn post, parse_amount, validate_date |

## Purpose

| Input | Valid | Rejected with exit 3 |

# FEATURE: Transfer

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Implements `ledger transfer <from> <to> <amount> <date>`, writing two TRANSFER rows atomically. |
| Depends On | FEATURE-TxnPost.md, FEATURE-LedgerCore.md, FEATURE-CliEntry.md, DATABASE.md |
| Provides | ledger transfer |
| Consumes | cli.main, parse_amount, format_amount, validate_date, balance_guard |

## Purpose

Move cash between two accounts as a pair of transactions in category `TRANSFER`. Both rows are stored or neither is.

## Trigger and Interface

`ledger transfer <from> <to> <amount> <date>` takes exactly four arguments.

| Condition | Exit | Stdout |
|-----------|------|--------|
| Transferred | 0 | Header `txn_id,date,account,category,amount,memo`, then the outgoing row, then the incoming row |
| Amount malformed, zero, or negative; date invalid; `from` equals `to`; either account unknown | 3 | Nothing |
| Amount exceeds the balance of `from` | 3 | Nothing |
| Wrong argument count | 2 | Nothing |
| Database unreachable or tables missing | 1 | Nothing |

One diagnostic line goes to standard error on every failure.

## Rows Written

| Row | Id | Account | Amount | Memo |
|-----|----|---------|--------|------|
| Outgoing | one more than the largest `txn_id` present, or 1 in an empty table | `<from>` | `-amount` | `transfer to <to>` |
| Incoming | the outgoing id plus one | `<to>` | `+amount` | `transfer from <from>` |

Both rows use category `TRANSFER` and the given date.

## Sequence

1. Check the argument count (usage error otherwise).
2. Parse the amount into integer cents; it must be positive. Validate the date. Require `from` and `to` to differ.
3. Confirm both accounts exist by listing accounts.
4. List transactions; compute the next id and the balance of `from`. Ask `balance_guard` whether subtracting the amount leaves `from` at or above zero.
5. Only after every check passes, write both rows in one database session, outgoing first. The writes use the transaction insert declared by FEATURE-TxnPost.md. A failure of either write leaves neither row stored.
6. Print the header and the two rows.

## Reads

Both accounts, and all transactions for the next id and the source balance.

## Writes

Two `transactions` rows, or none.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: confirm both accounts exist - supplies: `account` - returns: `account`, `name`
- `FEATURE-TXN-002` — read: list transactions for the next id and the source balance - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Implements `ledger load transactions <csv>`, which loads transactions keeping their file ids, all-or-nothing. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-CliEntry.md, FEATURE-LedgerCore.md, FEATURE-LoadAccounts.md, FEATURE-LoadCategories.md |
| Provides | ledger load transactions |
| Consumes | cli.main, parse_amount, validate_text, validate_date, balance_guard, ledger load accounts, ledger load categories |

## Purpose

Bulk-load transaction rows. Each loaded transaction keeps the `txn_id` written in its file. The
command either stores every row or stores nothing.

## Command Contract

`ledger load transactions <csv>` registers under the `load` command in the cli command table.

| Condition | Result |
|---|---|
| File readable, header equals `txn_id,date,account,category,amount,memo`, every row valid, resulting balances non-negative | Exit 0. Stdout is `table,loaded` then `transactions,<rows>`. |
| Missing `<csv>` argument or extra arguments | Exit 2, nothing on stdout. |
| File missing or unreadable | Exit 1, nothing on stdout. |
| Header mismatch; non-integer `txn_id`; bad date, amount, or memo | Exit 3, nothing stored. |
| Unknown account or unknown category | Exit 3, nothing stored. |
| A `txn_id` repeats within the file or already exists in the table | Exit 3, nothing stored. |
| Loading would leave any account balance below zero | Exit 3, nothing stored. |

## Behavior

1. Read the whole file with the standard `csv` module and check the header.
2. For each row validate the id, the date (a real calendar date), the amount (`-?DIGITS[.D[D]]`,
   never zero, parsed to integer cents), the memo (0 to 60 characters, no comma or newline), and
   that the account and category exist.
3. Reject repeated ids within the file and ids already stored.
4. Compute each touched account's stored balance plus the file's amounts with `balance_guard`; any
   result below zero rejects the file.
5. Only after every check passes, write all rows in one transaction, then print the result.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: confirm every named account exists - supplies: `account` - returns: `account`, `name`
- `FEATURE-CATEGORY-002` — read: confirm every named category exists - supplies: `category` - returns: `category`, `description`
- `FEATURE-TXN-002` — read: read existing ids and balances - supplies: `account`, `category` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

Rows are written through `db.transactions.create`, the operation declared for the post feature in
`DATABASE.md`; this feature reuses it and declares no operation of its own.

story proves that the projected balance of the source, computed from its stored transactions minus
the transfer amount, is checked before the first write. A rejected transfer exits `3`, writes nothing

## Purpose

`ledger report categories` prints, for every category ordered by code, how many transactions it has
and its inflow, outflow, and net, followed by a TOTAL row. Categories without transactions are
included. Every value is computed from the database at run time.

## Behavior

- Header row: `category,description,transactions,inflow,outflow,net`.
- One data row per category, ordered by category code, including categories with no transactions.
- `inflow` is the sum of positive amounts. `outflow` is the sum of the absolute values of negative
  amounts, written as a positive number. `net` is `inflow - outflow`.
- Final row: `TOTAL,,<count>,<inflow>,<outflow>,<net>`.
- Amounts are written with exactly two decimal places, a leading `-` when negative, and no
  thousands separator. Output is unquoted CSV with `\n` line endings; exit `0`.

## Database Interface

- `FEATURE-CATEGORY-002` — read: list every category in code order - supplies: `category` - returns: `category`, `description`
- `FEATURE-TXN-002` — read: list a category's transactions to total them - supplies: `category` - returns: `category`, `amount`
