### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Use the
existing Programmatic Acceptance format: a Python script with assertions against the built
product. Drydock executes each criterion through `languages/python/acceptance/runner.py`; `pytest -q`
runs the project test suite. Retain the criterion ID, observed values, stdout/stderr and result;
an assertion failure fails the check. The harness reports failure operands and available case
counts. Code coverage and persistence interactions require explicit instrumentation; record
available observations as key/value data associated with the criterion. Missing observations
are unknown, not proof that code or an interaction was unused.

### How does this language provide the shared persistence contract?

Use `stack/persistence.md`. Drydock copies `Rigging/languages/python/persistence/{db,sqlite,postgres}.py` and generates

# Command-Line Application

**Type:** cli
**Version:** 20260920 V1
**Tier:** platform
**Category:** Technologies
**Foundation:** cli
**Description:** Command-line application structure: entry point, argument parsing, exit codes, cross-platform launchers, and testing without spawning a process.

Technology reference. This file does not change between projects.

Prerequisites: `stack/common.md`, `languages/python/python.md`

---

## Foundation Contract

The published shape of this foundation. Drydock synthesizes the story that builds it and every
acceptance criterion writes against these names. Carried verbatim into `cli_compact.md`.

- package: cli
- entry: main(argv: list[str] | None = None) -> int
- fixture: cli_runner
- fixture_source: cli/testing.py

```python
# cli/__init__.py
def main(argv: list[str] | None = None) -> int:
    ...

# cli/testing.py
import contextlib
import io
from cli import main

def cli_runner(*args: str) -> tuple[int, str, str]:
    """Return (exit_code, stdout, stderr) without spawning a process."""
    out, err = io.StringIO(), io.StringIO()
    with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
        code = main(list(args))
    return code, out.getvalue(), err.getvalue()

# conftest.py
import pytest
from cli import testing

@pytest.fixture
def cli_runner():
    return testing.cli_runner
```

A criterion imports `cli_runner` from `cli.testing`, calls `cli_runner("status", "--json")`, and
asserts on the returned tuple. It does not call `subprocess.run`, which measures the installed
console script and the shell rather than the code the story wrote.

---

## 1. Directory Layout

**Rule**: Command code lives in `cli/`. The root holds only packaging and infrastructure files.

```
project/
  pyproject.toml            # [project.scripts] declares the console script
  cli/
    __init__.py             # main() — the single entry point
    commands.py             # one function per command; no argument parsing
    parser.py               # argparse construction; no behavior
  bin/
    run.sh                  # bash launcher
    run.ps1                 # PowerShell launcher
  tests/
```

**Why**: Parsing, behavior, and launching are three contracts. Collapsing them produces a command
that cannot be tested without a shell.

---

## 2. Entry Point and Exit Codes

**Rule**: `main(argv=None) -> int` parses, dispatches, and returns an exit code. It never calls
`sys.exit` and never raises for an expected failure. The console script is the only caller that
translates the return value into a process exit.

```python
# cli/__init__.py
import sys
from cli.parser import build_parser
from cli import commands

def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        return commands.dispatch(args)
    except OperationalError as exc:
        print(f"error: {exc}", file=sys.stderr)
        return 1
```

```toml
# pyproject.toml
[project.scripts]
mytool = "cli:main"
```

**Exit codes**: `0` success, `1` operational failure, `2` usage error. `argparse` already returns
`2` for a usage error; do not override it.

**Why**: A `main` that returns rather than exits is callable from a test in-process. A `main` that
calls `sys.exit` forces every criterion to spawn a subprocess and measure the shell.

---

## 3. Parsing Is Separate From Behavior

**Rule**: `parser.py` builds the `argparse` tree and returns it. `commands.py` holds one function
per command taking plain arguments, not a `Namespace`. Neither imports the other.

```python
# cli/parser.py
import argparse

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mytool")
    sub = parser.add_subparsers(dest="command", required=True)
    status = sub.add_parser("status", help="Report current state")
    status.add_argument("--json", action="store_true")
    return parser
```

```python
# cli/commands.py
def status(*, as_json: bool) -> int:
    ...

def dispatch(args) -> int:
    if args.command == "status":
        return status(as_json=args.json)
    return 2
```

**Why**: Behavior tested through a `Namespace` is behavior tested through the parser. Separating
them lets a criterion call `status(as_json=True)` directly.

---

## 4. Cross-Platform Launchers

**Rule**: Ship both launchers. They locate the environment and invoke the package entry point;
they contain no business logic. A launcher that makes a decision is a second implementation of the
command.

```bash
#!/usr/bin/env bash
# bin/run.sh — locate the environment and hand off. No business logic.
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
if [ -d "$ROOT/.venv" ]; then
    source "$ROOT/.venv/bin/activate"
fi
exec python -m cli "$@"
```

```powershell
# bin/run.ps1 — locate the environment and hand off. No business logic.
$ErrorActionPreference = "Stop"
$Root = Split-Path -Parent $PSScriptRoot
$Activate = Join-Path $Root ".venv\Scripts\Activate.ps1"
if (Test-Path $Activate) { & $Activate }
python -m cli @args
exit $LASTEXITCODE
```

```python
# cli/__main__.py — makes `python -m cli` work identically on both platforms
import sys
from cli import main

sys.exit(main())
```

**Why**: `python -m cli` is the one invocation both launchers share, so the two scripts cannot
drift in behavior — only in how they find the interpreter. `exit $LASTEXITCODE` is required in
PowerShell; without it the exit code is discarded and a failing command reports success.

---

## 5. Output and Streams

**Rule**: Results go to stdout, diagnostics to stderr. A `--json` mode prints one JSON document to
stdout and nothing else. Never interleave progress text into a machine-readable stream.

**Why**: A caller piping stdout to `jq` receives the progress lines too, and the command becomes
unusable in a pipeline.

---

## 6. Testing Without a Process

**Rule**: Test through `main(["status", "--json"])` or the `cli_runner` fixture. Reserve
`subprocess.run` for one packaging test asserting the installed console script exists and runs.

```python
def test_status_reports_json(cli_runner):
    code, out, err = cli_runner("status", "--json")
    assert code == 0
    assert json.loads(out)["state"] == "ready"
    assert err == ""
```

**Why**: In-process tests are fast, debuggable, and measure the code. Subprocess tests measure the
installed environment, which is a different and much smaller question.

---

# Persistence & Service Encapsulation — Contract Surface

## Relational Persistence

### Rule: persistence-boundary

All persistence and external-service access goes through typed encapsulation classes.

Constraints: Route, feature, and business-logic code must not execute raw SQL, read `os.environ`, open application files, import `sqlite3`/`psycopg`, or import cloud SDKs outside their encapsulation classes.

### function_open_database

Opens the generated persistence package using a database DSN.

| Parameter | Type |
|---|---|
| `dsn` | `str` |

Returns a `Database` instance with one attribute per declared table.

Constraints: Callers use the generated package and must not write repositories, DAOs, ORM models, connection helpers, session factories, or migrations.

### Database.<table>.<operation>

Executes a declared database operation using keyword arguments matching its `Input` fields.

| Input | Type |
|---|---|
| Declared operation fields | `str`, `int`, `float`, `bool`, or `bytes` |

Returns the declared operation `Output`: a row, `None`, a list of rows, or an integer row count.

Constraints: Unknown operations raise `UnknownOperation`. No other arguments, operators, OR conditions, joins, or SQL access paths are accepted. Calls are synchronous, and returned rows are frozen dataclasses without connection state.

### Rule: operation-kinds

Declared operations use one of six kinds: `get`, `list`, `create`, `update`, `upsert`, or `delete`.

Constraints: Operation names are the caller contract. Match fields select rows using AND semantics; bare fields use equality, and comparison terms may use `=`, `<`, `<=`, `>`, or `>=`. `list` filters are optional. `Order` controls list ordering. Every write executes as one package-level statement.

| Kind | Selection | Return |
|---|---|---|
| `get` | Unique-key match | Row or `None` |
| `list` | Optional input-field match | Ordered list of rows |
| `create` | None | Created row |
| `update` | Match, defaulting to primary key | Row/`None`, or count for many rows |
| `upsert` | Exactly one unique-key match | Inserted or replaced row |
| `delete` | Input-field match | Matched output/`None`, or count for many rows |

### Rule: operation-surface

Each operation exposes a generated contract containing its call path, kind, rows, match terms, sets, input schema, output schema, SQL, and 12-character SHA-256 contract fingerprint.

Constraints: Callers build against `DATABASE_compact.md`’s generated `Operation Surface`. Contract fingerprints change only when the operation name, kind, match, order, row behavior, return shape, or input/output field names and types change.

### Rule: database-runtime

The generated package supports SQLite and PostgreSQL selected from the runtime DSN.

Constraints: Both engines are present in every build. The schema is applied once during the DATABASE build step and is not created or altered at application startup.

# FEATURE: Usage Errors

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Every unknown command, unknown table or report, and wrong argument count exits 2 with nothing on standard output. |
| Depends On | FEATURE-CliEntry.md, FEATURE-Count.md, FEATURE-LoadAccounts.md, FEATURE-AccountAdd.md, FEATURE-TxnPost.md, FEATURE-Transfer.md, FEATURE-ReportBalances.md |
| Provides | usage error contract |
| Consumes | cli.main, ledger count, ledger load accounts, ledger account add, ledger txn post, ledger transfer, ledger report balances |

## Purpose

`ledger` distinguishes a malformed invocation (exit `2`) from a rejected one (exit `3`). A usage
error is detected from the argument vector alone, before the database is opened and before any
file is read, so it can never touch the store.

## Behavior

| Invocation | Exit |
|---|---|
| no arguments | `2` |
| unknown top-level command | `2` |
| `load` with a table other than `accounts`, `categories`, `transactions` | `2` |
| `report` with a report other than `balances`, `categories`, `monthly` | `2` |
| `account` or `txn` with an unknown subcommand | `2` |
| any command with too few or too many arguments | `2` |

Argument counts: `init` 0, `count` 0, `load` 2, `account add` 2, `account get` 1,
`account rename` 2, `account delete` 1, `txn post` 4 or 5, `txn get` 1, `txn amend` 2,
`txn delete` 1, `transfer` 4, `report` 1.

A usage error writes nothing to standard output and one diagnostic line to standard error.

## Database Interface

- None — persistence is owned by FEATURE-Count.md.

# FEATURE: Output Contract

| Field | Value |
|-------|-------|

## Purpose

Fixes what each command may put on each stream so the grader's byte-for-byte comparison of
standard output is stable.

## Behavior

- Every successful command except `init` writes one header row then data rows, comma-separated,
  with no quoting, no trailing spaces, and `\n` line endings, ending with a final `\n`.
- `init` writes nothing to standard output.
- A failing command (exit `1`, `2`, `3`, or `4`) writes nothing to standard output and exactly one
  diagnostic line to standard error.
- Money is written with exactly two decimals, a leading `-` when negative, and no thousands
  separator.
- The account row is `account,name,transactions,balance`; the transaction row is
  `txn_id,date,account,category,amount,memo`.

## Database Interface

- None — persistence is owned by FEATURE-AccountAdd.md.

# FEATURE: Database Resolution

| Field | Value |
|-------|-------|
| Version | 20261025 V1 |
| Description | Resolve the database from DATABASE_URL, then DATABASE_PATH, then data/app.db, selecting PostgreSQL or SQLite by prefix. |
| Depends On | FEATURE-Init.md, FEATURE-Count.md, FEATURE-CliEntry.md, DATABASE.md |
| Provides | database resolution, cli.database.resolve_database_dsn, cli.database.database_engine |
| Consumes | cli.main, ledger count, ledger txn post |

## Purpose

Every command opens the store through the shipped persistence library using one DSN chosen by a
single pure resolver. No driver is opened anywhere else and amounts stay integer cents.

## Interface

Module `cli/database.py`:

- `resolve_database_dsn(environ: Mapping[str, str]) -> str` returns `environ["DATABASE_URL"]` when
  set and non-empty, else `environ["DATABASE_PATH"]` when set and non-empty, else `data/app.db`.
  The value is returned unchanged and handed to `persistence.open_database`.
- `database_engine(dsn: str) -> str` returns `postgres` for a value beginning `postgres://` or
  `postgresql://`, and `sqlite` for anything else, including a `sqlite://` prefixed value.
- The command layer calls `resolve_database_dsn(os.environ)` once per invocation. A missing
  directory, unreachable server, or missing tables is exit `1`.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: list accounts to confirm the resolved store is reachable - supplies: `account` - returns: `account`, `name`

## Programmatic Acceptance
