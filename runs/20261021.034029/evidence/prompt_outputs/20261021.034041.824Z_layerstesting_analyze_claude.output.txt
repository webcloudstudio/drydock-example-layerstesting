## Planning Instructions

### Delivery Shape

The system is a Python 3.11+ command-line executable named `ledger` at the application root, backed by SQLite (or PostgreSQL when `DATABASE_URL` is a PostgreSQL DSN) through the shipped persistence library. Inputs are CLI arguments and CSV files. Outputs are CSV on standard output and diagnostics on standard error. Exit codes are 0, 1, 2, 3, and 4 per the contract. Execution flow: `init` creates schema; `load` populates seed data; commands mutate tables under atomic, balance-checked writes; reports are computed from the database at query time.

### Story Realization Map

- SCHEMA-001, SCHEMA-002: `sources/INSTRUCTIONS.md` Commands table; `sources/run.sh` A1, A2, Z1, Z2. Requires the schema capability and persistence library.
- LOAD-001..005: `sources/run.sh` B1..B4, D1..D3; fixtures `sources/seed_*.csv`. Requires load capability and atomic write transaction.
- REPORT-001..004: `sources/run.sh` C1..C3, H1..H3, U2; `sources/INSTRUCTIONS.md` Output section. Requires computed reports, no embedded answers.
- ACCT-001..004: `sources/run.sh` E1..E8. Requires account CRUD with in-use guard.
- TXN-001..004: `sources/run.sh` F1..F10, G3..G5. Requires transaction CRUD with rule checks.
- XFER-001: `sources/run.sh` G1, G2. Requires atomic two-row write.
- CLI-001, CLI-002: `sources/run.sh` U1, Z1, Z2. Requires argument dispatch and usage-error exit code 2.

### Test and Acceptance Strategy

Story-scoped tests run bounded slices of the application's own `bin/test.sh` where the story owns them. The terminal verification story runs the full supplied grader `sh sources/run.sh` and the full application `bin/test.sh`. Sea Trial st-001 is the sole acceptance verdict for the grader. No story runs the entire grader as a unit check.

### Sequencing and Dependencies

Build order: schema (SCHEMA-001) → counting (SCHEMA-002) → loads (LOAD-001..005) → account CRUD (ACCT-001..004) → transaction CRUD (TXN-001..004) → transfers (XFER-001) → reports (REPORT-001..004) → usage and reinitialization (CLI-001..002) → terminal full verification. Accounts and categories load before transactions. Balance-rule enforcement must exist before any mutating command is verified against negative-balance checks.

### Source Conflicts and Gaps

- No cross-source conflicts found. INSTRUCTIONS.md is the single definition for commands, output, and exit codes; run.sh is consistent with it.
- The Rigging catalog has no persistence-library component that matches `DATABASE.md`-generated access by name; the stack is recorded in TECHNOLOGY_STACK.md with conventional choices and does not block planning.
- Load rules for a non-empty target table are not stated in the sources. Per the narrowest consistent reading, `load` on a non-empty table is treated as an operation that adds rows only when every row passes validation and no key collides; a key collision is rejected with exit 3 (LOAD-005). This is recorded as an analysis choice, not a Commander decision.

# COMPASS: drydock Layers Testing Uat Case

## Compass
A command-line cash ledger for a small shop that records receipts and payments against cash places (drawers, a safe, petty cash) and produces balance, category, and monthly reports. It is built for a developer who must make the supplied grader pass exactly, with every command either completing fully or changing nothing.

## Constraints
- Executable named `ledger` at the application root.
- Python 3.11 or newer; tests run under pytest.
- All database access goes through the shipped persistence library; application code never opens a driver directly.
- Amounts are integer cents; no floating point.
- CSV output only: no quoting, no trailing spaces, `\n` line endings.
- Standard error is never compared by the grader.

## Guardrails
- Never read `sources/run.sh` from application code or embed report answers.
- Never modify, rewrite, regenerate, or substitute the read-only scoring assets.
- A rejected command changes nothing; a transfer stores both rows or neither.
- No command may leave any account balance below zero.
- Exit codes are exactly 0, 1, 2, 3, and 4 with the meanings in the contract.
