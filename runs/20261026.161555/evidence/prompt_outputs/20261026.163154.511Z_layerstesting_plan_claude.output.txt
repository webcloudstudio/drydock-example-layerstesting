# FEATURE: TxnGet

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | The `ledger txn get` command writes one stored transaction row by id. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-CliFoundation.md, FEATURE-CsvOutput.md, FEATURE-TxnPost.md |
| Provides | ledger txn get |
| Consumes | ledger_app.transactions.txn_row, cli.output.write_table, cli.registry.register |

## Questions

- None.

## Purpose

`ledger txn get <id>` reads one stored transaction and writes it as CSV. It is read-only and
never changes the store.

## Interface

| Item | Contract |
|------|----------|
| Command | `ledger txn get <id>`, exactly one argument |
| Success output | Header `txn_id,date,account,category,amount,memo`, then the one transaction row; amount has exactly two decimals |
| Exit 0 | The transaction exists |
| Exit 2 | Wrong argument count; one stderr line showing `ledger txn get <id>` |
| Exit 3 | The id is not a positive integer (`abc`, `0`, `-1`, `1.5`, empty); it is never reported as absent |
| Exit 4 | The id is a valid positive integer but no such transaction is stored |

## Behavior

1. Register the command in `cli.commands.txn_get` with arity 1 to 1 and the usage line above.
2. Parse the id: digits only, value at least 1. Anything else raises Rejected (exit 3).
3. Look the row up with `transactions.get`; none raises NotFound (exit 4).
4. Format the row with `txn_row` and call `write_table` as the final statement.
5. A failing command writes nothing to stdout.

## Database Interface

- `FEATURE-TRANSACTIONS-001` — read: get a transaction by id - supplies: `txn_id` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

## Programmatic Acceptance

import csv
import io
from decimal import Decimal

from cli.testing import cli_runner
from persistence.testing import db_session


def f(r, k):
    return r[k] if isinstance(r, dict) else getattr(r, k)


acct = "ZZTG1"
cat = "ZZTGC1"
day = "2026-05-01"
amount_text = "45.50"
cents = int(Decimal(amount_text) * 100)
memo = "walkin"
with db_session() as db:
    tid = max([f(r, "txn_id") for r in db.transactions.list()], default=0) + 1
    db.accounts.create(account=acct, name="Txn Get")
    db.categories.create(category=cat, description="Txn Get Cat")
    db.transactions.create(
        txn_id=tid, date=day, account=acct, category=cat, amount=cents, memo=memo
    )
    code, out, err = cli_runner("txn", "get", str(tid))
    print(out)
    print(err)
    assert code == 0
    rows = list(csv.reader(io.StringIO(out)))
    assert rows[0] == ["txn_id", "date", "account", "category", "amount", "memo"]
    assert rows[1] == [str(tid), day, acct, cat, amount_text, memo]
    assert len(rows) == 2

# FEATURE: TxnAmend

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | The `ledger txn amend` command changes only the amount of a stored transaction, subject to the balance rule. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-AmountValidation.md, FEATURE-BalanceGuard.md, FEATURE-CsvOutput.md, FEATURE-TxnPost.md |
| Provides | ledger txn amend |
| Consumes | ledger_app.transactions.txn_row, ledger_app.validation.amount_cents, ledger_app.balances.ensure_non_negative, cli.output.write_table |

## Questions

- None.

## Purpose

`ledger txn amend <id> <amount>` replaces the amount of one stored transaction and writes the
updated row. Nothing else about the transaction changes.

## Interface

| Item | Contract |
|------|----------|
| Command | `ledger txn amend <id> <amount>`, exactly two arguments |
| Success output | Header `txn_id,date,account,category,amount,memo`, then the updated row |
| Exit 0 | The amount was changed |
| Exit 2 | Wrong argument count; one stderr line showing `ledger txn amend <id> <amount>` |
| Exit 3 | The id is not a positive integer, the amount is invalid or zero, or the change would leave the account balance below zero |
| Exit 4 | The id is valid but no such transaction is stored |

## Behavior

1. Validate the id (positive integer) and the amount (`-?DIGITS[.D[D]]`, never zero) first; a
   bad value exits 3 even when the id is absent.
2. Look up the transaction with `transactions.get`; none raises NotFound (exit 4).
3. Compute the account's net change as the new cents minus the old cents and call
   `ensure_non_negative` on it before any write. Rejection leaves the store unchanged.
4. Call `transactions.update` with only `txn_id` and `amount`.
5. Transfer legs may be amended when the balance rule holds; pairing is not enforced.
6. Call `write_table` with the updated row as the final statement.

## Database Interface

- `FEATURE-TRANSACTIONS-001` — read: get a transaction by id - supplies: `txn_id` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TRANSACTIONS-002` — read: list an account's transactions for its balance - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TRANSACTIONS-004` — write: change a transaction amount - supplies: `txn_id`, `amount` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

# FEATURE: TxnDelete

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | The `ledger txn delete` command removes one stored transaction, subject to the balance rule. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-BalanceGuard.md, FEATURE-CsvOutput.md, FEATURE-TxnPost.md |
| Provides | ledger txn delete |
| Consumes | ledger_app.balances.ensure_non_negative, cli.output.write_table |

## Questions

- None.

## Purpose

`ledger txn delete <id>` removes one stored transaction and writes `deleted` and the id.

## Interface

| Item | Contract |
|------|----------|
| Command | `ledger txn delete <id>`, exactly one argument |
| Success output | Header-less two-row CSV: `deleted`, then the id |
| Exit 0 | The transaction was removed |
| Exit 2 | Wrong argument count; one stderr line showing `ledger txn delete <id>` |
| Exit 3 | The id is not a positive integer, or removal would leave the account balance below zero |

1. Validate the id as a positive integer; otherwise Rejected (exit 3).
2. Look the transaction up with `transactions.get`; none raises NotFound (exit 4).
3. Call `ensure_non_negative` with the change equal to minus the transaction amount for its
   account, before any write. Rejection leaves the store unchanged.
4. Call `transactions.delete`, then `write_table` with the single column `deleted` and the id as
   the final statement.
5. Transfer legs may be deleted when the balance rule holds; pairing is not enforced.

- `FEATURE-TRANSACTIONS-001` — read: get a transaction by id - supplies: `txn_id` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

# FEATURE: TransferRecord

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | The `ledger transfer` command records a paired debit and credit in category TRANSFER as one unit. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-BalanceGuard.md, FEATURE-CsvOutput.md, FEATURE-TxnPost.md |
| Provides | ledger transfer, ledger_app.transfers.record_transfer |
| Consumes | ledger_app.transactions.next_txn_id, ledger_app.transactions.txn_row, ledger_app.balances.ensure_non_negative, cli.output.write_table |

## Questions

- None.

## Purpose

`ledger transfer <from> <to> <amount> <date>` moves cash between two accounts by storing two
TRANSFER rows with consecutive ids, so total cash held is unchanged. This story delivers the
recording path for valid input; the rejection rules are specified in FEATURE-TransferRules.md.

## Interface

| Item | Contract |
|------|----------|
| Command | `ledger transfer <from> <to> <amount> <date>`, exactly four arguments |
| Success output | Header `txn_id,date,account,category,amount,memo`, then the outgoing row, then the incoming row |
| Outgoing row | Account `<from>`, category `TRANSFER`, amount `-amount`, memo `transfer to <to>`, id N |
| Incoming row | Account `<to>`, category `TRANSFER`, amount `+amount`, memo `transfer from <from>`, id N+1 |
| Id rule | N is one more than the largest stored `txn_id`, or 1 in an empty table |
| Library | `record_transfer(db, from_account, to_account, cents, date)` returns the two stored rows and is the single place both legs are written |

## Behavior

1. Register `transfer` in `cli.commands.transfer` with arity 4 to 4.
2. Parse the amount with `amount_cents` and the date with the date validator.
3. Obtain the first id from `next_txn_id`; the second is that id plus one.
4. Write the outgoing and incoming rows with `transactions.create` as the last step of the
   command, after every check, so that both legs are stored or neither.
5. Format both rows with `txn_row` and call `write_table` as the final statement.

## Database Interface

- `FEATURE-TRANSACTIONS-002` — read: list transactions to find the largest id and balances - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TRANSACTIONS-003` — write: store each transfer leg - supplies: `txn_id`, `date`, `account`, `category`, `amount`, `memo` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

# FEATURE: TransferRules

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | Rejection rules for `ledger transfer`, enforced before either leg is written. |
| Depends On | ARCHITECTURE.md, DATABASE.md, FEATURE-BalanceGuard.md, FEATURE-TransferRecord.md |
| Provides | ledger_app.transfers.validate_transfer |
| Consumes | ledger_app.transfers.record_transfer, ledger_app.balances.ensure_non_negative, ledger_app.validation.amount_cents, ledger_app.validation.date |

## Questions

- None.

## Purpose

A transfer is rejected with exit 3, with neither leg stored and nothing on stdout, when any rule
below fails. All rules are checked before the first write.

## Rules

| Rule | Rejected when |
|------|---------------|
| Amount | The amount is invalid, zero, negative, or has more than two decimals |
| Date | The date is not a real calendar date written `YYYY-MM-DD` |
| Distinct accounts | `<from>` and `<to>` are the same code |
| Known accounts | Either account is not stored |
| Category | The category `TRANSFER` is not stored |
| Balance | The source account balance after the transfer would be below zero |

## Behavior

1. `validate_transfer(db, from_account, to_account, cents, date)` runs the rules in the order
   above and raises Rejected on the first failure. It writes nothing.
2. The `transfer` command parses arguments, calls `validate_transfer`, calls
   `ensure_non_negative` with `{from: -cents, to: +cents}`, and only then calls
   `record_transfer`.
3. A transfer that leaves the source at exactly zero is allowed.

## Database Interface

- `FEATURE-ACCOUNTS-001` — read: confirm an account exists - supplies: `account` - returns: `account`, `name`
- `FEATURE-CATEGORIES-001` — read: confirm the TRANSFER category exists - supplies: `category` - returns: `category`, `description`
- `FEATURE-TRANSACTIONS-002` — read: list an account's transactions for its balance - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
