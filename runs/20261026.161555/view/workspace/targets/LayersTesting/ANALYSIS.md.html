Planning Instructions

Delivery Shape

This is a command-line ledger. Inputs are ledger command arguments, CSV files named on the load command, and the DATABASE_URL or DATABASE_PATH setting. Outputs are CSV on standard output for successful commands, one diagnostic line on standard error for failures, and exit codes 0 through 4.

Execution flow: init, then load accounts, load categories, and load transactions, then any mix of account, transaction, transfer, count, and report commands. Every write command validates all of its inputs and balance rules before its first write.

Persistence is three relational tables (accounts, categories, transactions) accessed only through the shipped persistence library. SQLite is the implemented and verified engine. All persisting commands are CLI consumers, so their repository-call contracts use consumer sensitivity data. Plan records these contracts in DATABASE.md with ids under the domains ACCOUNTS, CATEGORIES, TRANSACTIONS, and REPORTS.

Test and Acceptance Strategy

Focused story tests run each story's own pytest cases against a temporary database. Every story except ACCEPT-001 declares Suite: scoped, runs only the cases it owns, and never executes sources/run.sh.

ACCEPT-001 is the single terminal verification story. It declares Suite: full, depends on every implementation story, and runs sh sources/run.sh unfiltered. Its exit status is the complete-suite proof.

Sea Trials are separate from story tests. st-001 is the grader proof. st-004 through st-011 are deterministic proofs. st-012 through st-015 are guardrails verified by reviewed evidence.

Source Conflicts and Gaps

Under the unattended UAT policy, no blockers or questionnaires were emitted. Each open point below is resolved by the narrowest behavior consistent with the sources.

  1. Engine: the Stack section names SQLite as the implementation, while the Database section recognizes

PostgreSQL DSNs. Resolved: SQLite is the implemented and verified engine. DSN values are classified and routed to the persistence layer, but no PostgreSQL behavior is acceptance-verified.

  1. Persistence library: INSTRUCTIONS names a shipped persistence library and DATABASE.md, and neither is

among the imported sources. Resolved: the Technology Stack rows for persistence.md, sqlite.md, sqlalchemy.md, and alembic.md govern, and Plan authors DATABASE.md from the Database section.

  1. "Amounts ... never zero": resolved as zero-valued input amounts, including 0.00 and -0.00, being rejected with exit 3.
  2. Relative database paths: resolved against the application root.
  3. Missing parent directory for the default path: init creates it.
  4. Negative-balance timing: checked against the final balance each command would leave, not per row.
  5. txn amend and txn delete on a transfer leg: allowed when the balance rule holds. Neither command enforces transfer pairing.
  6. Posting directly to category TRANSFER: allowed, since TRANSFER is a loaded category.
  7. Non-integer transaction ids: rejected with exit 3.
  8. SQLAlchemy and Alembic: Rigging marks SQLAlchemy as superseded and Alembic as unused within a release. Resolved: the mandatory Python relational-persistence rule still selects both.
  9. Retired Sea Trial ids st-002, st-003, and st-009 are not reused.
  10. bin/test.sh is application-owned and names no tests. Resolved: TEST-001 defines its scope.
