# FEATURE: Validation

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Validate codes, names, memos, amounts, dates and transaction ids per the ledger rules. |
| Depends On | FEATURE-CliEntry.md |
| Provides | ledgerlib.validation |
| Consumes | cli.main |

## Questions

- None.

## Purpose

Every command validates its inputs before its first write. `ledgerlib/validation.py` is the single owner of the field rules in `sources/INSTRUCTIONS.md` Rules 3 to 6 and the transaction id rule. Each function raises `cli.errors.RejectedError` (exit 3) on violation and otherwise returns the validated value.

## Interface

| Function | Returns | Rule |
|----------|---------|------|
| `validate_code(value: str) -> str` | the value | 1 to 12 characters from `A-Z` and `0-9` |
| `validate_name(value: str) -> str` | the value | 1 to 40 characters, no comma, no newline (also used for descriptions) |
| `validate_memo(value: str) -> str` | the value | 0 to 60 characters, no comma, no newline |
| `parse_amount(text: str) -> int` | integer cents | matches `-?DIGITS[.D[D]]`, at most two decimals, never zero |
| `validate_date(text: str) -> str` | the value | real calendar date written `YYYY-MM-DD` |
| `parse_txn_id(text: str) -> int` | the integer | a non-empty string of decimal digits |

## Rules

- Amount parsing uses integer arithmetic on the digit strings only. No `float` or `Decimal`-free shortcut through floating point is permitted at any layer.
- `.5`, `5.`, `1.234`, `+5`, `1e3`, `0`, `0.0` and `0.00` are rejected.
- A date must match the `YYYY-MM-DD` shape exactly and be a real calendar date; `2026-02-30` is rejected.
- A transaction id with a sign, a decimal point, whitespace or no digits is rejected with exit 3.
- Validation reads no database and writes nothing.

## Database Interface

- None — persistence is owned by DATABASE.md.

# FEATURE: Ledger Rules

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Compute account views and projected balances, enforce the non-negative balance rule, and allocate transaction ids. |
| Depends On | DATABASE.md, FEATURE-CsvOutput.md, FEATURE-Validation.md |
| Provides | ledgerlib.rules |
| Consumes | persistence, ledgerlib.csvout |

## Questions

- None.

## Purpose

`ledgerlib/rules.py` owns the business rules every write command shares: an account's transaction count and balance, the projected balance after a set of changes, the rule that no balance goes below zero, and transaction id allocation. All reads go through `db.<table>.<operation>(...)`; balances are computed in Python from list rows in integer cents.

## Interface

| Function | Behavior |
|----------|----------|
| `account_view(db, code)` | Returns an object with `account`, `name`, `transactions` (count) and `balance` (integer cents), or `None` when the account is absent. |
| `balances_after(db, changes)` | `changes` is a list of `(account_code, delta_cents)` pairs. Returns a dict mapping each affected account to its balance after every change in the list is applied. |
| `require_non_negative(db, changes)` | Raises `cli.errors.RejectedError` (exit 3) when any account in the projected result would be below zero; returns `None` otherwise. Writes nothing. |
| `next_txn_id(db)` | Returns the largest stored `txn_id` plus one, or `1` when there are no transactions. |

## Rules

- The balance check is evaluated on each account's final balance after the whole change set, not change by change, so a set that dips below zero and recovers is accepted.
- A balance of exactly zero is accepted.
- Callers read `next_txn_id` and write the row inside one database transaction so two concurrent posts never receive the same id.
- Every check happens before the caller's first write; these functions perform no writes.
- No floating point is used for money.

## Database Interface

- `FEATURE-LEDGER-002` — read: get an account by code - supplies: `account` - returns: `account`, `name`
- `FEATURE-LEDGER-013` — read: list transactions, optionally for one account - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

# FEATURE: Init

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Implement `ledger init`, which prepares an empty ledger and removes existing rows when rerun. |
| Depends On | FEATURE-DatabaseSelection.md, DATABASE.md |
| Provides | ledger init |
| Consumes | ledgerlib.config, persistence |

## Questions

- None.

## Purpose

`ledger init` makes the configured database ready and empty. It creates the parent directory of the SQLite file when missing, opens the database through `open_database` (which provisions the declared tables idempotently), then removes every row, children first: transactions, then categories, then accounts. It writes nothing to standard output and exits 0.

## Behavior

- `cli/commands/init.py` exposes `run(args) -> list[str]` and returns no lines.
- Any argument is a usage error (exit 2).
- A PostgreSQL DSN or unreachable database exits 1 with nothing on standard output.
- Clearing uses the declared `clear` operations with the lowest possible bound (`min_txn_id` of a value below every id, empty-string bounds for codes). No driver import and no DDL outside the persistence library.
- Rerunning on a populated ledger removes every row, leaving all three tables empty.
- Creating a missing parent directory is covered by the project's own pytest suite, which owns temporary database locations.

## Database Interface

- `FEATURE-LEDGER-006` — write: clear accounts from a code upward - supplies: `min_account`
- `FEATURE-LEDGER-010` — write: clear categories from a code upward - supplies: `min_category`
- `FEATURE-LEDGER-016` — write: clear transactions from an id upward - supplies: `min_txn_id`

# FEATURE: Load Accounts

| Field | Value |
|-------|-------|
| Version | 20261027 V1 |
| Description | Implement `ledger load accounts <csv>` as an all-or-nothing bulk load. |
| Depends On | FEATURE-DatabaseSelection.md, FEATURE-Validation.md, FEATURE-CsvOutput.md, DATABASE.md |
| Provides | ledger load accounts |
| Consumes | ledgerlib.config, ledgerlib.validation, ledgerlib.csvout |

## Questions

- None.

## Purpose

`cli/commands/load.py` owns `ledger load <table> <csv>` with a per-table handler registry; an unknown table is a usage error (exit 2). This story adds the `accounts` handler. The whole file is accepted or none of it is stored.

## Behavior

- The header must be exactly `account,name`; any other header is rejected with exit 3.
- Every data row must have the header's field count; each code and name is validated with `ledgerlib.validation`.
- A duplicate code within the file, or one already stored, is rejected with exit 3.
- Every check completes before the first write. Writes happen in one database transaction, so a rejected file stores nothing.
- A file that cannot be read exits 1 with nothing on standard output.
- A header-only file loads zero rows, prints `accounts,0`, and exits 0.
- Output is `table,loaded` followed by `accounts,<rows>`.
- Missing arguments or extra arguments are a usage error (exit 2).

## Database Interface

- `FEATURE-LEDGER-001` — write: create an account - supplies: `account`, `name` - returns: `account`, `name`
- `FEATURE-LEDGER-002` — read: get an account by code - supplies: `account` - returns: `account`, `name`

## Programmatic Acceptance
