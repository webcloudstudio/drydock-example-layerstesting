## Foundation Contract

- package: cli
- entry: main(argv: list[str] | None = None) -> int

```python
# cli/__init__.py
def main(argv: list[str] | None = None) -> int:
    ...

# cli/testing.py
import contextlib
import io
from cli import main

def cli_runner(*args: str) -> tuple[int, str, str]:
    """Return (exit_code, stdout, stderr) without spawning a process."""
    out, err = io.StringIO(), io.StringIO()
    with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
        code = main(list(args))
    return code, out.getvalue(), err.getvalue()

# conftest.py
import pytest

@pytest.fixture
def cli_runner():
    return testing.cli_runner
```

A criterion imports `cli_runner` from `cli.testing`, calls `cli_runner("status", "--json")`, and
asserts on the returned tuple. It does not call `subprocess.run`, which measures the installed
console script and the shell rather than the code the story wrote.

---

## 1. Directory Layout

**Rule**: Command code lives in `cli/`. The root holds only packaging and infrastructure files.

```
project/
  pyproject.toml            # [project.scripts] declares the console script
  cli/
    __init__.py             # main() — the single entry point
    commands.py             # one function per command; no argument parsing
    parser.py               # argparse construction; no behavior
  bin/
    run.sh                  # bash launcher
    run.ps1                 # PowerShell launcher
  tests/
```

**Why**: Parsing, behavior, and launching are three contracts. Collapsing them produces a command
that cannot be tested without a shell.

---

## 2. Entry Point and Exit Codes

**Rule**: `main(argv=None) -> int` parses, dispatches, and returns an exit code. It never calls
`sys.exit` and never raises for an expected failure. The console script is the only caller that
translates the return value into a process exit.

```python
# cli/__init__.py
import sys
from cli.parser import build_parser
from cli import commands

def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    try:
        return commands.dispatch(args)
    except OperationalError as exc:
        print(f"error: {exc}", file=sys.stderr)
        return 1
```

```toml
# pyproject.toml
[project.scripts]
mytool = "cli:main"
```

**Exit codes**: `0` success, `1` operational failure, `2` usage error. `argparse` already returns
`2` for a usage error; do not override it.

**Why**: A `main` that returns rather than exits is callable from a test in-process. A `main` that
calls `sys.exit` forces every criterion to spawn a subprocess and measure the shell.

---

## 3. Parsing Is Separate From Behavior

**Rule**: `parser.py` builds the `argparse` tree and returns it. `commands.py` holds one function
per command taking plain arguments, not a `Namespace`. Neither imports the other.

```python
# cli/parser.py
import argparse

def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="mytool")
    sub = parser.add_subparsers(dest="command", required=True)
    status = sub.add_parser("status", help="Report current state")
    status.add_argument("--json", action="store_true")
    return parser
```

```python
# cli/commands.py
def status(*, as_json: bool) -> int:
    ...

def dispatch(args) -> int:
    if args.command == "status":
        return status(as_json=args.json)
    return 2
```

**Why**: Behavior tested through a `Namespace` is behavior tested through the parser. Separating
them lets a criterion call `status(as_json=True)` directly.

---

## 4. Cross-Platform Launchers

**Rule**: Ship both launchers. They locate the environment and invoke the package entry point;
they contain no business logic. A launcher that makes a decision is a second implementation of the
command.

```bash
#!/usr/bin/env bash
# bin/run.sh — locate the environment and hand off. No business logic.
set -euo pipefail
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
if [ -d "$ROOT/.venv" ]; then
    source "$ROOT/.venv/bin/activate"
fi
exec python -m cli "$@"
```

```powershell
# bin/run.ps1 — locate the environment and hand off. No business logic.
$ErrorActionPreference = "Stop"
$Root = Split-Path -Parent $PSScriptRoot
$Activate = Join-Path $Root ".venv\Scripts\Activate.ps1"
if (Test-Path $Activate) { & $Activate }
python -m cli @args
exit $LASTEXITCODE
```

```python
# cli/__main__.py — makes `python -m cli` work identically on both platforms
import sys
from cli import main

sys.exit(main())
```

**Why**: `python -m cli` is the one invocation both launchers share, so the two scripts cannot
drift in behavior — only in how they find the interpreter. `exit $LASTEXITCODE` is required in
PowerShell; without it the exit code is discarded and a failing command reports success.

---

## 5. Output and Streams

**Rule**: Results go to stdout, diagnostics to stderr. A `--json` mode prints one JSON document to
stdout and nothing else. Never interleave progress text into a machine-readable stream.

**Why**: A caller piping stdout to `jq` receives the progress lines too, and the command becomes
unusable in a pipeline.

---

## 6. Testing Without a Process

**Rule**: Test through `main(["status", "--json"])` or the `cli_runner` fixture. Reserve
`subprocess.run` for one packaging test asserting the installed console script exists and runs.

```python
def test_status_reports_json(cli_runner):
    code, out, err = cli_runner("status", "--json")
    assert code == 0
    assert json.loads(out)["state"] == "ready"
    assert err == ""
```

**Why**: In-process tests are fast, debuggable, and measure the code. Subprocess tests measure the
installed environment, which is a different and much smaller question.

# FEATURE: Load Transactions

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Implements `ledger load transactions <csv>` keeping file txn_ids, with all-or-nothing validation and balance checking. |
| Depends On  | ARCHITECTURE.md, DATABASE.md, FEATURE-CliFoundation.md, FEATURE-BalanceRules.md, FEATURE-LoadAccounts.md, FEATURE-LoadCategories.md |
| Provides    | ledger load transactions |
| Consumes    | transactions.create, transactions.get, accounts.get, categories.get, check_balances |

## Purpose

Bulk-load transactions from a CSV file whose header is exactly
`txn_id,date,account,category,amount,memo`. Each loaded row keeps the `txn_id` from its file. The
command checks every row and the resulting balances before its first write.

## Trigger

`./ledger load transactions <csv>`

## Sequence

1. Reject a wrong argument count with exit 2.
2. Read the file. An unreadable file exits 1.
3. Require the exact header; any other header exits 3.
4. Validate every row: `txn_id` is an integer; the date is a real calendar date `YYYY-MM-DD`; the
   amount matches `-?DIGITS[.D[D]]`, has at most two decimals, and is never zero; the memo is 0 to
   60 characters with no comma or newline. Amounts are parsed to integer cents without floating point.
5. Reject (exit 3) a `txn_id` repeated within the file or already stored, an account absent from
   `accounts`, and a category absent from `categories`.
6. Apply the whole file to the stored balances through `check_balances`; if any account balance
   would be below zero after the file is applied, exit 3 (Decision Q-004: final balances are checked).
7. Only then write all rows through `transactions.create`, keeping each file `txn_id`.
8. Print `table,loaded` and `transactions,<rows>`.

A failing command writes nothing to standard output and one diagnostic line to standard error.

## Reads

- `transactions.get`, `accounts.get`, `categories.get` for validation; stored transactions via `check_balances`.

## Writes

- `transactions.create` once per validated row, after all validation has passed.

## Database Interface

- `FEATURE-TRANSACTIONS-001` — write: create a transaction - supplies: `txn_id`, `date`, `account`, `category`, `amount`, `memo` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TRANSACTIONS-002` — read: find a stored transaction by id - supplies: `txn_id` - returns: `txn_id`, `account`, `amount`
- `FEATURE-ACCOUNTS-002` — read: find a stored account by code - supplies: `account` - returns: `account`
- `FEATURE-CATEGORIES-002` — read: find a stored category by code - supplies: `category` - returns: `category`

# FEATURE: Txn Post

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | The `ledger txn post` command validates and stores one new transaction and prints its row. |
| Depends On  | FEATURE-BalanceRules.md, FEATURE-CliFoundation.md, DATABASE.md |
| Provides    | ledger txn post |
| Consumes    | transactions.create, transactions.list, accounts.get, categories.get, check_balances |

## Purpose

`ledger txn post <account> <category> <amount> <date> [<memo>]` records one receipt or payment
against an account. The command checks every input and the resulting balance before its first
write, so a rejected post changes nothing.

## Trigger

An operator runs `./ledger txn post` with four or five arguments.

## Sequence

1. Reject a wrong argument count with exit 2 (fewer than four or more than five arguments after `post`).
2. Validate the account code, category code, amount, date, and memo with the shared validators. Any invalid value exits 3.
3. Look up the account with `accounts.get` and the category with `categories.get`. An unknown account or category exits 3.
4. Convert the amount to integer cents. Zero and amounts with more than two decimal places exit 3.
5. List the account's transactions with `transactions.list` and run `check_balances` with the proposed added row. A balance below zero exits 3.
6. List all transactions with `transactions.list`, take the largest `txn_id` plus one (or `1` when none exist) as the new id.
7. Store the row with `transactions.create`, then print the header row and the stored row as CSV. Exit 0.

## Output

```text
txn_id,date,account,category,amount,memo
<id>,<date>,<account>,<category>,<amount with two decimals>,<memo>
```

An omitted memo is stored and printed as an empty field. Failures write one diagnostic line to standard error and nothing to standard output.

## Reads

- `accounts.get`, `categories.get`, `transactions.list`

## Writes

- `transactions.create`, only after every check has passed

## Database Interface

- `FEATURE-TRANSACTIONS-001` — write: create the new transaction - supplies: `txn_id`, `date`, `account`, `category`, `amount`, `memo` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TRANSACTIONS-003` — read: list transactions to find the largest id and the account balance - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-ACCOUNTS-002` — read: confirm the account exists - supplies: `account` - returns: `account`, `name`
