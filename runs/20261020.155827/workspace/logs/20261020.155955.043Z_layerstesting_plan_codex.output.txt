# ARCHITECTURE: Ledger Application

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Defines the command-line ledger boundaries, configuration precedence, transactional services, and persistence access rules. |
| Depends On  | — |
| Provides    | ledger application boundaries, configuration boundary, persistence boundary |
| Consumes    | — |

## Questions

- None.

## Purpose

The application is a Python command-line cash ledger. The executable routes validated commands to transactional services, which use the generated `persistence` package for all database access.

## Technology Stack

- Python 3.11 or newer: application and tests.
- SQLite: default relational database.
- CLI: executable `ledger` at the application root.
- pytest: project test suite.
- POSIX Shell: `bin/test.sh`.
- Shipped persistence library: exclusive database access boundary.

## Module Ownership

| Boundary | Owner | Responsibility |
|---|---|---|
| CLI routing | `cli` and root `ledger` launcher | Parse commands, validate usage, map outcomes to exit codes, and emit CSV. |
| Configuration | application configuration module | Resolve `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`. |
| Validation | validation services | Validate codes, text fields, amounts, dates, references, and balances. |
| Transactions | command services | Execute each command within one database transaction and roll back rejected changes. |
| Reporting | report services | Query and aggregate stored integer cents without embedded report values. |
| Persistence | generated `persistence` package | Own connections, schema operations, and repository calls. Application code never opens a database driver. |
| Test harness | `bin/test.sh` and pytest suite | Exercise the completed application against temporary databases. |

## Command Flow

`ledger` resolves configuration, dispatches a command, opens the configured database through `persistence.open_database`, begins one transaction, validates and performs the operation, emits success CSV, and commits. Any failure rolls back and emits one diagnostic line to standard error.

## Data Rules

Amounts are integer cents at every application and persistence boundary. Account balances are sums of transaction amounts and must remain non-negative after every mutating command. Reports derive all values from database queries.

- Reports must be computed from stored data.

## Configuration

The database DSN is resolved in this order:

1. `DATABASE_URL`
2. `DATABASE_PATH`
3. `data/app.db`

A `postgres://` or `postgresql://` URL selects PostgreSQL. Other values select SQLite, with an optional `sqlite://` prefix.

## Schema

## `accounts`

| Field | Type | Notes |
|---|---|---|
| `account` | TEXT PRIMARY KEY NOT NULL | Account code. |
| `name` | TEXT NOT NULL | Account name. |

## `categories`

| Field | Type | Notes |
|---|---|---|
| `category` | TEXT PRIMARY KEY NOT NULL | Category code. |
| `description` | TEXT NOT NULL | Category description. |

## `transactions`

| Field | Type | Notes |
|---|---|---|
| `txn_id` | INTEGER PRIMARY KEY NOT NULL | Transaction identifier. |
| `date` | TEXT NOT NULL | Calendar date in `YYYY-MM-DD` form. |
| `account` | TEXT NOT NULL REFERENCES accounts(account) | Account code. |
| `category` | TEXT NOT NULL REFERENCES categories(category) | Category code. |
| `amount` | INTEGER NOT NULL | Signed amount in cents. |
| `memo` | TEXT NOT NULL | Optional memo, empty when omitted. |

## Persistence Interface

Application callers use `open_database(dsn)` and declared operations on `db.accounts`, `db.categories`, and `db.transactions`. SQL, driver connections, and table access remain inside the shipped persistence package.

## Programmatic Acceptance

- None. Drydock owns generated schema construction and persistence connectivity invariants deterministically.

## User Acceptance

- None.

## Guardrails

- All database access must go through the shipped persistence library.
- Amounts must remain integer cents; floating point is forbidden.
- Foreign keys must enforce valid account and category references.
- Schema creation must be idempotent.
- Every command must execute as one transaction.

# FEATURE: CLI Foundation

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Provides the executable ledger command, dispatch, configuration resolution, CSV output, and exit-code behavior. |
| Depends On  | ARCHITECTURE.md, DATABASE.md |
| Provides    | ./ledger executable, command dispatch, usage validation, exit-code mapping |
| Consumes    | ledger application boundaries, ledger persistence operations |

## Questions

- None.

## Purpose

The root executable `ledger` is the only user-facing entry point. It dispatches supported commands and maps outcomes to the contract's exit codes.

## Configuration

Resolve the database location from `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`. The resolved value is passed to the shipped persistence library.

## Command Contract

Successful commands emit CSV to standard output. Failures emit no standard output and one diagnostic line to standard error.

| Exit code | Meaning |
|---|---|
| 0 | Success |
| 1 | Operational failure |
| 2 | Usage error |
| 3 | Rejected input or rejected state change |
| 4 | Requested record not found |

Unknown commands, reports, tables, and incorrect argument counts return exit code 2.

## Programmatic Acceptance

# FEATURE: Schema Lifecycle

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Implements ledger initialization and ordered row counting. |

| Provides    | ledger init, ledger count |

## Questions

- None.

## Behavior

`ledger init` drops and recreates the accounts, categories, and transactions tables, leaving all three empty and producing no output.

`ledger count` reports rows in the fixed order accounts, categories, transactions using:

```text
table,rows
```

# FEATURE: Account and Category Loading

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Loads validated account and category CSV files atomically through the ledger CLI. |
| Depends On  | FEATURE-SCHEMA-LIFECYCLE.md, DATABASE.md |
| Provides    | ledger load accounts, ledger load categories |
| Consumes    | ./ledger executable, ledger persistence operations |

## Questions

- None.

## Inputs

Account files must have the header `account,name`. Category files must have the header `category,description`. Codes contain 1–12 uppercase letters or digits. Names and descriptions contain 1–40 characters and no commas or newlines.

Each load is one transaction. Duplicate keys, malformed headers, unreadable files, invalid fields, or constraint violations reject the entire batch with exit code 3 for rejected data or 1 for operational failure.

## Output

A successful load emits:

```text
table,loaded
<table>,<rows>
```

## Programmatic Acceptance

=== AC load-accounts-round-trip ===
Intent: A valid account CSV loads and becomes visible in the count and account interface.

import os
import subprocess
import tempfile
from pathlib import Path

accounts = "account,name\nA1,Main\nA2,Reserve\n"

with tempfile.TemporaryDirectory() as directory:
    database = Path(directory) / "ledger.db"
    csv_file = Path(directory) / "accounts.csv"
    csv_file.write_text(accounts)
    env = {**os.environ, "DATABASE_URL": str(database)}

    initialized = subprocess.run(["./ledger", "init"], capture_output=True, text=True, env=env)
    print(initialized.stdout)
    print(initialized.stderr)
    assert initialized.returncode == 0

    loaded = subprocess.run(["./ledger", "load", "accounts", str(csv_file)], capture_output=True, text=True, env=env)
    print(loaded.stdout)
    print(loaded.stderr)
    assert loaded.returncode == 0

    counted = subprocess.run(["./ledger", "count"], capture_output=True, text=True, env=env)
    print(counted.stdout)
    print(counted.stderr)
    assert counted.returncode == 0
    assert counted.stdout.splitlines()[1] == "accounts,2"
