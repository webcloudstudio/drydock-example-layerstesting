# FEATURE: Amount Rules

| Field       | Value |
|-------------|-------|
| Version     | 20261021 V1 |
| Description | Parses input amounts into integer cents and formats stored cents for output. |
| Depends On  | ARCHITECTURE.md |
| Provides    | amount parse and format helpers |
| Consumes    | |

## Questions

- None.

## Purpose

Every command that accepts or prints an amount uses one codec. Input matches `-?DIGITS[.D[D]]` with at most two decimal places and is never zero. Output has exactly two decimal places, a leading `-` when negative, and no thousands separator.

## Behavior

- `parse_amount(text: str) -> int` returns integer cents. `"12.5"` yields `1250`; `"-12.50"` yields `-1250`; `"5000"` yields `500000`.
- Input that does not match `-?DIGITS[.D[D]]`, has more than two decimal places, or equals zero raises `ValueError`.
- `format_amount(cents: int) -> str` returns exactly two decimals: `1250` gives `12.50`, `0` gives `0.00`, `-1250` gives `-12.50`, `500000` gives `5000.00`.
- No floating point is used at any step.

# FEATURE: Text Rules

| Field       | Value |
|-------------|-------|
| Version     | 20261021 V1 |
| Description | Validates account and category codes, account names, category descriptions, and memos. |
| Depends On  | ARCHITECTURE.md |
| Provides    | code, name, and memo validators |
| Consumes    | |

## Questions

- None.

## Purpose

Every input string that becomes a stored code, name, description, or memo passes one validator before any write. Limits are checked in characters, and no value may contain a comma or newline.

## Behavior

- `validate_code(text: str) -> str` accepts 1 to 12 characters drawn from `A-Z` and `0-9`.
- `validate_name(text: str) -> str` accepts 1 to 40 characters for account names and category descriptions.
- `validate_memo(text: str) -> str` accepts 0 to 60 characters.
- Any value containing a comma or a newline is rejected for every validator.
- Rejection raises `ValueError`; the returned value is the input unchanged when accepted.

- None.

## Purpose

Every command that accepts a transaction date validates it before any write. Only a real calendar date in `YYYY-MM-DD` form is accepted.

## Behavior

- `validate_date(text: str) -> str` returns the input unchanged when it is a real calendar date in `YYYY-MM-DD` form.

# FEATURE: Balance Rules

| Field       | Value |
|-------------|-------|
| Version     | 20261021 V1 |
| Description | Checks that no command leaves any account balance below zero before it writes. |
| Depends On  | ARCHITECTURE.md, FEATURE-Rules-Amount.md |
| Provides    | balance check |
| Consumes    | |

## Questions

- None.

## Purpose

An account balance is the sum of its transaction amounts. Posting, amending, deleting, transferring, and loading each compute every resulting balance and refuse the command if any would be negative, before the first write.

## Behavior

- `check_balances(resulting: dict[str, int]) -> None` takes the resulting balance in integer cents for each affected account code.
- If any value is below zero, it raises `ValueError` naming the account code; otherwise it returns `None`.
- The check runs after the candidate change is computed and before any row is written.

## Programmatic Acceptance

=== AC balance-accept-non-negative ===
Intent: Resulting balances that are all zero or positive pass the check.
Suite: scoped

from rules.balance import check_balances

check_balances({"SAFE": 0, "PETTY": 25000})
=== END AC balance-accept-non-negative ===

=== AC balance-reject-negative ===
Intent: A resulting balance below zero raises ValueError.
Suite: scoped

from rules.balance import check_balances

try:
    check_balances({"PETTY": -1})
except ValueError:
    pass
else:
    raise AssertionError("negative balance was accepted")
=== END AC balance-reject-negative ===

=== AC balance-reject-any-account ===
Intent: One negative account among several rejects the whole check.
Suite: scoped

- No command that would leave a balance below zero writes any row.

# FEATURE: Load Core

| Field       | Value |
|-------------|-------|
| Version     | 20261021 V1 |
| Description | Shared CSV parsing, row validation, and all-or-nothing writes for the three load commands. |
| Depends On  | ARCHITECTURE.md, FEATURE-CLI-Entry.md, FEATURE-Database-Location.md, FEATURE-Rules-Amount.md, FEATURE-Rules-Text.md, FEATURE-Rules-Date.md, FEATURE-Rules-Balance.md |
| Provides    | ledger load <table> <csv> |
| Consumes    | |

## Questions

- None.

## Purpose

`ledger load <table> <csv>` dispatches to the loader for `accounts`, `categories`, or `transactions`. The three loaders share one path: read the file, validate the header and every row, check balances for transactions, and write nothing unless every row passes.

## Behavior

- The header must match the table's columns in the order given by `sources/INSTRUCTIONS.md`.
- A file that cannot be read exits `1` with no standard output.
- A header or row that fails validation, an unknown account or category, or a resulting negative balance exits `3` and writes no rows.
- On success the command writes `table,loaded` then `<table>,<rows>` to standard output and exits `0`.
- A header-only file loads zero rows and exits `0`.

## Programmatic Acceptance

## Guardrails
