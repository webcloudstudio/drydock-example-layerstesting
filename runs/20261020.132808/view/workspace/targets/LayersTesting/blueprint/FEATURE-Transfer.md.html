Feature: Transfer

FieldValue
Version20261020 V1
DescriptionStore a transfer as two TRANSFER rows, or neither, under the non-negative balance rule.
Depends OnDATABASE.md, FEATURE-Transaction-Post.md, FEATURE-Balance-Rule.md, FEATURE-Amount-Format.md, FEATURE-Date-Validation.md, FEATURE-Code-Validation.md, FEATURE-CLI-Output.md, FEATURE-CLI-Dispatch.md
Providesledger transfer <from> <to> <amount> <date>
Consumesaccounts.get, transactions.create, transactions.list

Purpose

ledger transfer <from> <to> <amount> <date> moves cash between two accounts. It stores two rows in category TRANSFER: -amount on <from> and +amount on <to>. Both rows are stored or neither is.

Trigger

The user runs ledger transfer <from> <to> <amount> <date>.

Behavior

  1. Validate syntax before any lookup: <amount> parses as a positive amount, and <date> is a

real YYYY-MM-DD date. Either failure exits 3.

  1. Require <from> and <to> to differ. Equal accounts exit 3.
  2. Within the command transaction, confirm both accounts exist through accounts.get. A missing

account exits 3, not 4.

  1. Take the next two ids: n and n+1, where n is one more than the largest txn_id present

(1 in an empty table), using the shared next-id function from FEATURE-Transaction-Post.md.

  1. Create the row n on <from> with amount -amount and memo transfer to <to>, and the row

n+1 on <to> with amount +amount and memo transfer from <from>. Both use category TRANSFER.

  1. Apply the balance rule to both touched accounts (FEATURE-Balance-Rule.md). A negative balance

exits 3 and rolls back both rows.

  1. Commit and print the two rows in CSV with the header:
txn_id,date,account,category,amount,memo
<n>,<date>,<from>,TRANSFER,-<amount>,transfer to <to>
<n+1>,<date>,<to>,TRANSFER,<amount>,transfer from <from>

Amounts are written with exactly two decimal places (FEATURE-Amount-Format.md).

=== AC transfer-stores-two-rows ===
Intent: A valid transfer stores two TRANSFER rows with the next two ids and the stated memos.
Requires: executable=python3; scope=test

from persistence.testing import db_session from cli.testing import cli_runner

with db_session() as db: db.accounts.create(account="XFA1", name="Transfer From") db.accounts.create(account="XFB1", name="Transfer To") db.categories.create(category="TRANSFER", description="Internal transfer") db.transactions.create(txn_id=8001, date="2026-05-01", account="XFA1", category="TRANSFER", amount=5000, memo="seed") code, out, err = cli_runner("transfer", "XFA1", "XFB1", "100.00", "2026-05-02") assert code == 0 assert db.transactions.get(txn_id=8002).account == "XFA1" assert db.transactions.get(txn_id=8002).amount == -10000 assert db.transactions.get(txn_id=8002).memo == "transfer to XFB1" assert db.transactions.get(txn_id=8003).account == "XFB1" assert db.transactions.get(txn_id=8003).amount == 10000 assert db.transactions.get(txn_id=8003).memo == "transfer from XFA1" === END AC transfer-stores-two-rows ===

User Acceptance

  • None.

Guardrails

  • Both rows are stored or neither; no partial transfer is ever visible.
  • Transfer ids come from the shared next-id function, never from a separately stored counter.
  • A rejected transfer prints nothing to standard output.
