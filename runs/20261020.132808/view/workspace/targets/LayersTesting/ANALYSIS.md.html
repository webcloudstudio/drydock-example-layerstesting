Commander Expectations

  • assert every command either completes in full or changes nothing
  • assert every report is computed from the database and never embeds a known answer
  • assert the supplied sources/run.sh grader exits zero unmodified against the completed application
  • assert all database access goes through the shipped persistence library, selected by DATABASE_URL

Planning Instructions

Delivery Shape

The system is a command-line program. Inputs are the ledger subcommand arguments, CSV files named on the command line, and the environment variables DATABASE_URL and DATABASE_PATH. Outputs are CSV on standard output for successful commands, one diagnostic line on standard error for failures, an exit code from the table in the brief, and database state changed only by commands that succeed.

The persistence boundary is the single store module. Three tables are created by init: accounts (account primary key, name), categories (category primary key, description), and transactions (txn_id integer primary key, date, account referencing accounts, category referencing categories, amount integer cents, memo). Plan records the exact contract in DATABASE.md. Every command, including reports, reads and writes through that boundary.

The bin/test.sh wrapper is POSIX sh and runs pytest against a temporary SQLite database.

Source Conflicts and Gaps

No blockers or questionnaires are emitted under the unattended UAT policy. Each ambiguity is resolved below by the narrowest behavior consistent with the sources.

  • Persistence library not supplied. The brief names a "shipped persistence library" and a relational layer generated from DATABASE.md, but neither is in the sources. Resolution: Plan authors the store module and the generated layer under DB-001 through DB-004 and SCHEMA-001, governed by Rigging persistence.md.
  • Amount "never zero". Resolution: a zero input amount in any form exits 3 (AC-013).
  • PostgreSQL DSN. The brief defines the DSN prefix but builds over SQLite. Resolution: the prefix is recognized and fails with exit 1 (AC-003). No PostgreSQL behavior is acceptance-tested.
  • Pytest versus POSIX bin/test.sh. Resolution: bin/test.sh is a POSIX wrapper that runs pytest.
  • Validation precedence. Resolution: argument syntax (exit 3) is checked before lookups (exit 4), and unknown referenced accounts or categories exit 3 (AC-010, AC-011, AC-014).
  • Non-integer ids. Resolution: exit 3 (AC-012).
  • Help text. The brief does not define help output. Resolution: help text appears in the stderr usage diagnostic only; no help command is added (CLI-002, AC-001).
  • Concurrency. The sources say nothing about concurrent writers. Resolution: each command is one transaction; lock contention exits 1 with no change (DB-003, AC-004).
  • Balance check scope. Resolution: DB-004 checks every account touched by the command after its changes and before commit.
  • Header-only and mismatched files. Resolution: a header-only file loads zero rows (AC-005); a mismatched header exits 3 (AC-006).
  • Relative database path. Resolution: data/app.db resolves against the working directory.
  • Authentication and sensitive data. The sources state no auth model. This is a local single-user CLI handling no secrets. Resolution: no authentication is added, and no sensitive-data controls beyond the rules above.
  • Amount magnitude. No limit is stated. Resolution: no limit beyond the storage integer type.
