Attribute Stories to Source Requirements

You are the lineage attribution agent. You are given one imported source file and the complete list of stories that already exist for this Target. Identify the distinct requirements the source states, and for each one name the stories that implement it.

This is a matching task against a closed set. Every story you may name is listed in <stories>. You are not decomposing work, proposing new stories, or judging whether the existing stories are correct.

Method

  1. Read the source and identify each distinct requirement it states. A requirement is a thing the

system must do, at whatever granularity the author wrote it. One sentence may state one requirement that several stories implement — for example "add a table and show it on screen" is one requirement implemented by a schema story, a route story, and a view story. Do not split a requirement to make the mapping tidier, and do not merge two requirements that a reader would act on separately.

  1. Give each requirement a short kebab-case name that describes it. The name is an identifier, not

a summary: mark-book-read, not the-reader-can-mark-a-book-as-read.

  1. For each requirement, list every story that implements any part of it. A story may implement

more than one requirement; a requirement may need more than one story.

  1. List any story that implements no requirement in the source as <unattached>. This is expected

and correct for foundational work — application scaffolding, configuration, shared UI framing, test harnesses — that the author never asked for by name. Do not force such a story onto an unrelated requirement.

Rules

  • Use only story ids that appear in <stories>. Never invent one.
  • Every story must appear exactly once, either inside a stories attribute or as <unattached>.
  • Quote the requirement text verbatim from the source in the tag body. Do not paraphrase it.
  • Emit nothing but the tags below. No preamble, no commentary, no explanation.

</requirement>

Build Instructions: A Cash Ledger

Objective

Build a command-line cash ledger for a small shop. The shop keeps cash in a few places (drawers, a safe, petty cash), records every receipt and payment against one of those places, and asks for three reports: balances by account, totals by category, and totals by month.

The product is an executable named ledger at the application root. It stores everything in a relational database through the shipped persistence library, and every command either completes in full or changes nothing.

Stack

Implement in Python 3.11 or newer over SQLite, through the shipped Python persistence library. Tests run under pytest. The contract below is the same for every language and database: the same commands, the same output, and the same exit codes.

Run Harness

sources/run.sh is the scoring entry point. It is supplied, not authored, and is staged verbatim into the application root with the seed files. drydock uat runs sh sources/run.sh from the completed application root and takes its exit code and output as the score.

The harness creates a fresh database, runs ./ledger init, loads the seed files, and then runs a fixed sequence of 43 checks. Each check compares one command's exit code and standard output with a known answer. Standard error is never compared. The harness prints PASS or FAIL per check and ends with:

LayersTesting: NN passed, NN failed (of 43)

Read-only scoring assets

These files are the exam. Do not modify, rewrite, regenerate, or substitute them:

  • sources/run.sh — the scoring entry point and its known answers
  • sources/seed_accounts.csv — 4 accounts
  • sources/seed_categories.csv — 7 categories
  • sources/seed_transactions.csv — 120 transactions, January to March 2026
  • sources/seed_transactions_bad.csv — 11 transactions; row 11 names an unknown account

Application code never reads sources/run.sh and never embeds a report answer. Every report is computed from the database.

Database

DATABASE_URL names the database. A value beginning postgres:// or postgresql:// is a PostgreSQL DSN. Any other value is a SQLite file path, optionally prefixed sqlite://. When DATABASE_URL is unset, DATABASE_PATH is used, then data/app.db.

Three tables. Amounts are stored as integer cents and never as floating point.

TableColumnsKeys
accountsaccount text, name textprimary key account
categoriescategory text, description textprimary key category
transactionstxn_id integer, date text YYYY-MM-DD, account text, category text, amount integer cents, memo textprimary key txn_id; account references accounts; category references categories

All database access goes through the shipped persistence library and the relational layer generated from DATABASE.md. Application code never opens a database driver directly.

Rules

  1. Every command is one database transaction. A command that fails for any reason leaves

every table exactly as it was. A load that rejects row 11 stores none of rows 1 to 10. A transfer stores both of its rows or neither.

  1. No command leaves an account balance below zero. An account's balance is the sum of its

transaction amounts. Posting, amending, deleting, transferring, and loading are all subject to this rule, checked after the command's changes and before it commits.

  1. Codes (account, category) are 1 to 12 characters from A-Z and 0-9.
  2. Names and descriptions are 1 to 40 characters. Memos are 0 to 60 characters. None of

them contains a comma or a newline.

  1. Amounts on input match -?DIGITS[.D[D]]: at most two decimal places, never zero. On output

an amount is written with exactly two decimal places, a leading - when negative, and no thousands separator: -12.50, 0.00, 5000.00.

  1. Dates are real calendar dates written YYYY-MM-DD. 2026-02-30 is rejected.
  2. Transaction ids. A loaded transaction keeps the txn_id from its file. A posted

transaction receives one more than the largest txn_id present, or 1 in an empty table. A transfer's outgoing row takes that id and its incoming row the next.

Output

Every successful command except init writes CSV to standard output: one header row, then data rows, comma-separated, no quoting, no trailing spaces, \n line endings. init writes nothing. A failing command writes nothing to standard output and one diagnostic line to standard error.

The account row is account,name,transactions,balance, where transactions counts the account's transactions. The transaction row is txn_id,date,account,category,amount,memo.

Commands

CommandOutput on success
ledger initDrops all three tables if present and creates them empty. Nothing written.
ledger counttable,rows, then accounts, categories, transactions rows in that order.
ledger load <table> <csv>Loads accounts, categories, or transactions from a file whose header matches the table's columns in the order above. Writes table,loaded and <table>,<rows>.
ledger account add <code> <name>The new account row.
ledger account get <code>The account row.
ledger account rename <code> <name>The updated account row.
ledger account delete <code>deleted and the code. Refused while the account has transactions.
ledger txn post <account> <category> <amount> <date> [<memo>]The new transaction row.
ledger txn get <id>The transaction row.
ledger txn amend <id> <amount>The updated transaction row. Only the amount changes.
ledger txn delete <id>deleted and the id.
ledger transfer <from> <to> <amount> <date>Two transaction rows in category TRANSFER: -amount on <from> with memo transfer to <to>, then +amount on <to> with memo transfer from <from>. The amount is positive and the accounts differ.
ledger report balancesaccount,name,transactions,balance per account ordered by code, then TOTAL,,<count>,<sum>.
ledger report categoriescategory,description,transactions,inflow,outflow,net per category ordered by code, including categories with no transactions, then TOTAL,,<count>,<inflow>,<outflow>,<net>.
ledger report monthlymonth,transactions,inflow,outflow,net per YYYY-MM that has transactions, ascending, then TOTAL,<count>,<inflow>,<outflow>,<net>.

inflow is the sum of positive amounts. outflow is the sum of the absolute values of negative amounts, written as a positive number. net is inflow - outflow.

Exit codes

CodeMeaning
0Success.
1Operational failure: database unreachable, tables missing, file unreadable.
2Usage error: unknown command, unknown table or report, wrong argument count.
3Rejected: invalid code, name, amount, date, or file row; duplicate key; unknown account or category; account in use; any change that would leave a negative balance.
4Not found: account get/rename/delete of an absent account, txn get/amend/delete of an absent id.

Tests
