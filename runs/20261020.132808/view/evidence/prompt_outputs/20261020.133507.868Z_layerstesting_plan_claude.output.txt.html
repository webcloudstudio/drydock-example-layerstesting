# FEATURE: Command Transaction

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Runs every ledger command inside exactly one database transaction that commits on success and rolls back on failure. |
| Depends On  | FEATURE-Database-Location.md, DATABASE.md |
| Provides    | run_command(db, command) |
| Consumes    | open_database, db.accounts.create, db.accounts.list |

## Questions

- None.

## Purpose

Every command that reads or writes the store runs inside one transaction. A command either completes in full or changes nothing.

## Behavior

- `run_command(db, command)` opens one transaction on `db`, calls `command(db)` once, commits when the call returns, and returns the value the command returned.
- If `command` raises, every write made through `db` during that call is rolled back, and the exception propagates unchanged.
- A persistence error raised while the transaction is open, including a write lock held by another connection, rolls back the same way and propagates. The CLI maps it to exit 1 through FEATURE-Operational-Errors.md.
- The wrapper does not commit or roll back inside a command body. Commands never open their own transaction.

## Programmatic Acceptance

=== AC command-transaction-commits ===
Intent: A command that returns normally has its write persisted and its return value passed back to the caller.

from persistence.testing import db_session
from transaction import run_command

account_code = "TXNA1"
account_name = "Commit Test"

with db_session() as db:
    result = run_command(db, lambda d: d.accounts.create(account=account_code, name=account_name))
    assert result.account == account_code
    matches = [row for row in db.accounts.list() if row.account == account_code]
    assert len(matches) == 1
    assert matches[0].name == account_name
=== END AC command-transaction-commits ===

=== AC command-transaction-rolls-back-all-writes ===
Intent: When a command raises after two writes, neither write persists and the exception reaches the caller.

from persistence.testing import db_session
from transaction import run_command

first_code = "TXNB1"
second_code = "TXNB2"

class Abort(Exception):
    pass

def write_then_fail(d):
    d.accounts.create(account=first_code, name="Rollback First")
    d.accounts.create(account=second_code, name="Rollback Second")
    raise Abort("forced after two writes")

with db_session() as db:
    before = len(db.accounts.list())
    raised = False
    try:
        run_command(db, write_then_fail)
    except Abort:
        raised = True
    assert raised
    after = db.accounts.list()
    assert len(after) == before
    assert all(row.account not in (first_code, second_code) for row in after)
=== END AC command-transaction-rolls-back-all-writes ===

- None.

## Guardrails

- No module begins or commits a transaction outside `run_command`.
- A failed command never leaves a partial write in any table.
- No command body commits its own work.
- Application code reaches the store only through the `persistence` package, never through a database driver.

# FEATURE: Schema Init

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Implements `ledger init`, which drops and recreates the three ledger tables empty. |
| Depends On  | FEATURE-Command-Transaction.md, FEATURE-CLI-Dispatch.md, DATABASE.md |
| Provides    | ledger init |
| Consumes    | open_database, run_command |

## Questions

- None.

## Purpose

`ledger init` resets the store to three empty tables, so a later load or report starts from a known state.

## Behavior

- `ledger init` drops `accounts`, `categories`, and `transactions` if they exist, then recreates them empty from the generated schema through the `persistence` package.
- The drop and recreate run inside one command transaction (FEATURE-Command-Transaction.md).
- `init` writes nothing to standard output and exits 0.
- Argument-count errors are rejected by FEATURE-CLI-Dispatch.md before this handler runs.

# FEATURE: Schema Count

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Implements `ledger count`, which prints the row count of each ledger table. |
| Depends On  | FEATURE-Schema-Init.md, FEATURE-CLI-Output.md, DATABASE.md |
| Provides    | ledger count |
| Consumes    | open_database, write_csv |

## Questions

- None.

## Purpose

`ledger count` tells an operator how many rows each table holds, which is how the seed loads are checked.

## Behavior

- Prints `table,rows`, then one line each for `accounts`, `categories`, and `transactions`, in that order.
- Each count is the number of rows returned by that table's list operation in `DATABASE.md`. No count is stored or hardcoded.
- The output is written through `write_csv`, so the contract in FEATURE-CLI-Output.md applies.
- Exits 0 on success.

# FEATURE: CLI Dispatch

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Routes `ledger` command words to their handlers and rejects usage errors with exit 2 before any database access. |
| Depends On  | FEATURE-CLI-Platform.md |
| Provides    | ledger <command> routing, usage error exit 2 |
| Consumes    | cli.main, cli_runner |

## Questions

- None.

## Purpose

Every `ledger` invocation is either handed to the handler its story owns or rejected as a usage error. Nothing else happens first.

## Behavior

- The command word, sub-verb, and argument count are checked against the Commands table before any handler or database access runs.
- An unknown command, unknown sub-verb, unknown table, unknown report, or wrong argument count exits 2 with exactly one line on standard error and nothing on standard output.
- A correctly shaped command is passed to its handler, and the handler's exit code is returned unchanged.

## Programmatic Acceptance

=== AC cli-dispatch-usage-errors-exit-two ===
Intent: Each unknown command, sub-verb, table, report, or wrong argument count exits 2 with empty stdout and one stderr line.

# FEATURE: CLI Output

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Provides the CSV writer every successful ledger command uses for standard output. |
| Depends On  | FEATURE-CLI-Platform.md |
| Provides    | cli.output.write_csv(header, rows) |
| Consumes    | none |

## Questions

- None.

## Purpose

Every successful command except `init` reports its result as CSV on standard output, in one shared format.

## Behavior

- `write_csv(header, rows)` writes the header row, then one row per entry in `rows`, to standard output.
- Fields are joined with commas, are never quoted, and each line ends with a single `\n`.
- No line carries a trailing space, and no line contains a carriage return.
- With an empty `rows`, only the header row is written.
- Nothing is written to standard error.

## Programmatic Acceptance

=== AC cli-output-header-then-rows ===
Intent: `write_csv` writes the header row followed by one comma-separated line per data row, in order.

import contextlib
import io
