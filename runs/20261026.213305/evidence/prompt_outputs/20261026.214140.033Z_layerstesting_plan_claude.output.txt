# FEATURE: Balance Rules

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | Judge every affected account balance on the final state of a command and reject any negative balance before a write. |
| Depends On | DATABASE.md, FEATURE-ErrorContract.md |
| Provides | balance_rules.check_final_balances |
| Consumes | persistence.open_database, ledger_errors.Rejected |

## Questions

- None.

## Purpose

Rule 2 of the source says no command leaves an account balance below zero. Every command that
writes transactions (load, post, amend, delete, transfer) calls this one check before its first
write. An account's balance is the sum of its stored transaction amounts in integer cents.

## Interface

Module `balance_rules`, importable from the application root.

`check_final_balances(db, inserts=(), amount_changes=(), deletions=())` returns `None` or raises
`ledger_errors.Rejected`.

| Argument | Meaning |
|----------|---------|
| `db` | An open persistence `Database` (from `open_database` or `db_session`). |
| `inserts` | Iterable of `(account, amount_cents)` pending new rows. |
| `amount_changes` | Iterable of `(txn_id, new_amount_cents)` replacing a stored row's amount. |
| `deletions` | Iterable of `txn_id` of stored rows to be removed. |

## Rules

- Read stored rows only through `db.transactions.list(account=...)` and `db.transactions.get(txn_id=...)`.
- For each account touched by any pending change, compute `stored sum + pending inserts + amount deltas - deleted amounts`, in Python `int` cents. No floating point.
- Judge only the final state after all pending changes. An intermediate dip that a later pending change restores is allowed, whatever the order of the arguments.
- If any touched account's final balance is below zero, raise `Rejected`. A balance of exactly zero is allowed.
- The check performs no write of any kind.
- A `txn_id` in `amount_changes` or `deletions` that is not stored is ignored here; the calling command reports it as not found before calling this check.
- The message of `Rejected` never contains a DSN or credential.

## Database Interface

- `FEATURE-TXN-003` — read: list a transaction set by account - supplies: `account` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`
- `FEATURE-TXN-002` — read: get a transaction by id - supplies: `txn_id` - returns: `txn_id`, `date`, `account`, `category`, `amount`, `memo`

## Programmatic Acceptance

# FEATURE: CLI Usage

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | Reject unknown commands, tables, reports and wrong argument counts with exit 2 and usage text on standard error only. |
| Depends On | FEATURE-CliFoundation.md, FEATURE-ErrorContract.md |
| Provides | ledger usage |
| Consumes | ledger.register_command, ledger_errors.UsageError |

## Questions

- None.

## Purpose

Any invocation that is not a valid command shape exits 2 before any database access. The usage
text is derived from the command table and names every command and sub-verb.

## Rules

- No arguments, an unknown command, an unknown `load` table, an unknown `report`, an unknown sub-verb of `account` or `txn`, or the wrong number of arguments for a known command all raise `UsageError`, which the top-level handler maps to exit 2.
- Argument counts follow the command table: `init` 0, `count` 0, `load` 2, `account add` 2, `account get` 1, `account rename` 2, `account delete` 1, `txn post` 4 or 5, `txn get` 1, `txn amend` 2, `txn delete` 1, `transfer` 4, `report <name>` 0.
- Usage text goes to standard error only. It lists `init`, `count`, `load`, `account add|get|rename|delete`, `txn post|get|amend|delete`, `transfer`, and `report balances|categories|monthly`.
- Standard output stays empty and the database is neither opened nor changed.
- Argument-count validation happens before any value validation, so a command with a wrong count never exits 3.

## Database Interface

- None — this Blueprint reaches no repository.

# FEATURE: Ledger Init

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | Implement `ledger init` to prepare an empty ledger and remove all rows when rerun. |
| Depends On | FEATURE-CliFoundation.md, FEATURE-ErrorContract.md, DATABASE.md |
| Provides | ledger init |
| Consumes | ledger.register_command, ledger_config.database_dsn, persistence.open_database, ledger_errors.OperationalFailure |

## Questions

- None.

## Purpose

`ledger init` leaves the ledger empty and ready for loading. The tables are created by the
DATABASE step; `init` only removes rows and never issues DDL.

## Rules

- Register `init` through `ledger.register_command`; it takes no arguments.
- In one database transaction delete every transaction, then every category, then every account (`db.transactions.delete_all()`, `db.categories.delete_all()`, `db.accounts.delete_all()`), so foreign keys hold at each step.
- Write nothing to standard output. Exit 0.
- Rerunning on an empty or populated ledger always succeeds and leaves zero rows in all three tables.
- The database is resolved by `DATABASE_URL` (an empty value counts as unset), then `DATABASE_PATH` (used only when `DATABASE_URL` is unset), then `data/app.db`.
- An unreachable database or missing tables raises `OperationalFailure` (exit 1). The diagnostic never contains the DSN, a path credential or a password.

## Database Interface

- `FEATURE-TXN-006` — write: delete every transaction - supplies: none - returns: none
- `FEATURE-CATEGORY-006` — write: delete every category - supplies: none - returns: none
- `FEATURE-ACCOUNT-006` — write: delete every account - supplies: none - returns: none

## Programmatic Acceptance

# FEATURE: Load Accounts

| Field | Value |
|-------|-------|
| Version | 20261026 V1 |
| Description | Implement `ledger load accounts <csv>` as an all-or-nothing bulk load. |
| Depends On | FEATURE-LedgerInit.md, FEATURE-Validation.md, FEATURE-CsvOutput.md, FEATURE-ErrorContract.md, DATABASE.md |
| Provides | ledger load accounts |
| Consumes | ledger.register_command, persistence.open_database, validation.check_code, validation.check_text, csv_output.write_rows, ledger_errors.Rejected, ledger_errors.OperationalFailure |

## Questions

- None.

## Purpose

Load account records from a CSV file. The whole file is checked before the first write, so a
rejected file stores nothing.

## Rules

- Register the `accounts` table under `load`; the command takes the table name and one file path.
- An unreadable file raises `OperationalFailure` (exit 1).
- Parse the whole file with the standard `csv` module. The header must equal `account,name` exactly, in names and order; any other header raises `Rejected` (exit 3) before any row is stored. An empty file counts as a wrong header.
- Every data row must have exactly two fields. Validate `account` with `validation.check_code` and `name` with `validation.check_text` (1 to 40 characters, no comma or newline). Any bad row rejects the file.
- A code that repeats within the file, or that already exists in the store (`db.accounts.get`), rejects the whole file. Account names may repeat across accounts.
- Only after every check passes, insert all rows with `db.accounts.create` in one database transaction. If an insert fails the transaction rolls back and nothing is stored.
- A header-only file loads zero rows.
- On success write `table,loaded` and `accounts,<rows>` through `csv_output.write_rows` and exit 0. A failure writes nothing to standard output.

## Database Interface

- `FEATURE-ACCOUNT-002` — read: check whether an account code already exists - supplies: `account` - returns: `account`, `name`
- `FEATURE-ACCOUNT-001` — write: create an account - supplies: `account`, `name` - returns: `account`, `name`
