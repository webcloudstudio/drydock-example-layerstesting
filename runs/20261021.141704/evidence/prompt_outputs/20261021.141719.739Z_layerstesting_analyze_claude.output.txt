# Blueprint Analysis: LayersTesting

## Commander Expectations

- assert `sh sources/run.sh` exits zero against the completed ledger.
- assert a rejected command exits with its documented code and changes nothing.
- assert no command leaves an account balance below zero.
- assert every report is computed from the database and matches the known answers.
- assert all storage goes through the generated persistence layer selected by `DATABASE_URL`.

## Story List

### Feature: Command Line Interface

| ID | Story | High-level AC |
|---|---|---|
| CLI-001 | Ledger executable at the application root | `ledger` is an executable at the application root that dispatches every command. |
| CLI-002 | Usage errors | Unknown command, table, or report, and wrong argument count exit 2 with empty stdout. |
| CLI-003 | Help text for every command | `--help` lists every command, and each command and sub-verb has usage help text. |
| CLI-004 | CSV success output and failure diagnostics | Successful commands write a header and comma-separated rows with `\n` endings; failures write nothing to stdout and one stderr line. |
| CLI-005 | Amount output format | Output amounts have exactly two decimals, a leading `-` when negative, and no thousands separator. |

### Feature: Database Access

| ID | Story | High-level AC |
|---|---|---|
| DB-001 | Database selection | `DATABASE_URL` selects the store; otherwise `DATABASE_PATH`, then `data/app.db`; `postgres://` and `postgresql://` select PostgreSQL. |
| DB-002 | Generated persistence access | The three tables are reached only through the generated relational layer, and each write command commits in one database transaction. |
| DB-003 | Integer-cent amount storage | Amounts are stored as integer cents and never as floating point. |
| DB-004 | Operational failure | An unreachable database or missing table exits 1 with one stderr line. |

### Feature: Schema Lifecycle

| ID | Story | High-level AC |
|---|---|---|
| SCHEMA-001 | Initialize empty schema | `init` drops any present tables, creates the three tables empty, and writes nothing. |
| SCHEMA-002 | Row counts | `count` writes `table,rows`, then the accounts, categories, and transactions rows. |

### Feature: Input Validation

| ID | Story | High-level AC |
|---|---|---|
| VAL-001 | Code validation | Account and category codes are 1 to 12 characters from `A-Z` and `0-9`. |
| VAL-002 | Name, description, and memo validation | Names and descriptions are 1 to 40 characters, memos 0 to 60, and none contains a comma or newline. |
| VAL-003 | Amount input validation | Amounts match `-?DIGITS[.D[D]]`, have at most two decimals, and are never zero. |
| VAL-004 | Date validation | Dates are real calendar dates written `YYYY-MM-DD`. |
| VAL-005 | Non-negative balance guard | Any command that would leave an account below zero exits 3 before its first write. |

### Feature: Accounts

| ID | Story | High-level AC |
|---|---|---|
| ACCT-001 | Add account | `account add` writes the new row with 0 transactions and balance 0.00; a duplicate code exits 3. |
| ACCT-002 | Get account | `account get` writes the row; an absent code exits 4. |
| ACCT-003 | Rename account | `account rename` writes the updated row; an absent code exits 4. |
| ACCT-004 | Delete account | `account delete` writes `deleted` and the code; an account with transactions exits 3; an absent code exits 4. |

### Feature: Bulk Load

| ID | Story | High-level AC |
|---|---|---|
| LOAD-001 | Load accounts | `load accounts` checks the header, validates every row, rejects duplicate keys, and stores all rows or none. |
| LOAD-002 | Load categories | `load categories` follows the same all-or-nothing contract for categories. |
| LOAD-003 | Load transactions | `load transactions` keeps each file `txn_id`, rejects unknown accounts or categories, and applies the balance guard. |
| LOAD-004 | File readability and header check | An unreadable file exits 1; a header that does not match the table's columns exits 3. |

### Feature: Transactions

| TXN-004 | Delete transaction | `txn delete` writes `deleted` and the id, applies the balance guard, and exits 4 when the id is absent. |

### Feature: Transfers

### Feature: Reports

## Planning Instructions

### Delivery Shape

The product is a single-process Python command-line program, the `ledger` executable at the application root, invoked once per command. Inputs are argv and CSV files named by `load`. State lives in a relational store: SQLite by default, PostgreSQL when `DATABASE_URL` is a PostgreSQL DSN. Outputs are CSV on stdout, one diagnostic line on stderr for failures, and an exit code from 0 to 4. Each command validates all inputs and the balance guard, then performs its writes in one database transaction. The supplied `sh sources/run.sh` drives acceptance from the application root.

### Test and Acceptance Strategy

Each story other than ACC-001 proves itself with a focused pytest slice it owns and declares `Suite: scoped`. The supplied `sources/run.sh` accepts no scope selector, so no non-terminal story runs it. ACC-001 is the single terminal verification story. It depends on every other story and declares `Suite: full` in its heading block. It runs `sh sources/run.sh` unfiltered and passes only when every supplied check passes. Sea Trial st-001 proves the same verdict.

### Sequencing and Dependencies

Build order: CLI-001, then DB-001 and DB-002, then SCHEMA-001 and SCHEMA-002. Next come the validation stories VAL-001 through VAL-005, then the accounts stories ACCT-001 through ACCT-004. LOAD-001 and LOAD-002 follow the accounts and categories work. Then TXN-001 through TXN-004, LOAD-003, and XFER-001. Reports (RPT-001 to RPT-003) come after the write stories. CLI-002 through CLI-005 and DB-003 and DB-004 are built with the foundation. TEST-001 follows the feature stories, TEST-002 follows TEST-001, and ACC-001 is last. The seed files and `sources/run.sh` are staged before ACC-001 runs. External dependencies are Python 3.11 or newer, SQLite, pytest, and POSIX `sh`.

### Source Conflicts and Gaps

- No cross-source conflicts were found. `sources/INSTRUCTIONS.md` and `sources/run.sh` agree on every command, output row, and exit code.
- The shipped persistence library is not among the sources. It is treated as the layer generated from `DATABASE.md` under the persistence catalog entry, and DB-002 covers it.
- PostgreSQL is named by the DSN rule while this build is SQLite. DB-001 requires recognition and routing of a PostgreSQL DSN; the grader verifies only SQLite.
- No help-text format is stated. CLI-003 synthesizes it.
- The sources state no authentication model. The product is a local command-line tool with no protected resource, so none is specified.
- Each command's concurrency is bounded by one database transaction, per DB-002 and AC-002.
