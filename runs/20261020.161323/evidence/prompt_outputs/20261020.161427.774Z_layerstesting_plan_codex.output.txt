# ARCHITECTURE: Ledger Application Boundaries

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Defines the command-line ledger boundaries, configuration flow, and persistence ownership. |
| Depends On  | — |
| Provides    | application module boundaries, configuration boundary, persistence boundary |
| Consumes    | — |

## Questions

- None.

## Purpose

The application is a Python 3.11+ command-line executable named `ledger`. It accepts commands and arguments, validates complete operations before writing, and emits deterministic CSV on success. Diagnostics are written to standard error.

## Modules and Ownership

| Boundary | Owner | Responsibility |
|---|---|---|
| Executable | `ledger` | Application-root entry point and process exit status |
| CLI | `cli` | Argument parsing, command dispatch, output formatting, and error mapping |
| Configuration | CLI/application configuration module | Resolve `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db` |
| Validation | Domain validation module | Codes, text fields, amounts, dates, identifiers, references, and balance rules |
| Services | Ledger command services | Atomic preflight, mutations, account lifecycle, loading, transfers, and reports |
| Persistence | `persistence` | Exclusive database access through generated shipped operations |
| Test runner | `bin/test.sh` | Invoke the project pytest suite from the application root |

Application code must not import or open a database driver directly. Services call the shipped persistence package and keep database details behind that boundary.

## Command Groups

- Lifecycle: `ledger init`, `ledger count`
- Loading: `ledger load accounts`, `ledger load categories`, `ledger load transactions`
- Accounts: `ledger account add`, `get`, `rename`, `delete`
- Transactions: `ledger txn post`, `get`, `amend`, `delete`
- Transfer: `ledger transfer`
- Reports: `ledger report balances`, `categories`, `monthly`

## Error Contract

Exit status `0` indicates success, `1` operational failure, `2` usage error, `3` rejected input or business rule, and `4` absent account or transaction. Successful commands write CSV except `init`; failures write no standard output and one diagnostic line to standard error.

## Technology Stack

- Python 3.11 or newer implements the application and tests.
- SQLite is the local relational database.
- The shipped Python persistence library is the only database access boundary.
- The CLI is the root executable interface.
- pytest runs the automated suite.
- POSIX shell runs `bin/test.sh` and the supplied conformance harness.

## Configuration

Resolve the database DSN in this order:

1. `DATABASE_URL`
2. `DATABASE_PATH`
3. `data/app.db`

A `postgres://` or `postgresql://` value selects PostgreSQL. Any other value is a SQLite path, optionally prefixed with `sqlite://`. Application callers use `persistence.open_database(dsn)` and never open a driver directly.

| Field | Type | Notes |

## Persistence Rules

All writes are preceded by complete validation. Foreign keys are enforced. Transactions are atomic. Amounts are represented only as integers in persistence and formatted to two decimal places at the CLI boundary.

# FEATURE: Ledger Validation

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Defines shared validation and atomic preflight rules for ledger commands. |
| Depends On  | ARCHITECTURE.md, DATABASE.md, FEATURE-Persistence-Lifecycle.md |
| Provides    | domain validation, integer-cent amount parsing, date validation, balance validation |
| Consumes    | relational ledger schema, persistence operations |

## Questions

- None.

## Purpose

All commands validate their complete input and all resulting business rules before their first write.

## Validation Rules

- Codes are 1–12 uppercase alphanumeric characters.
- Names and descriptions are 1–40 characters.
- Memos are 0–60 characters.
- Names, descriptions, and memos contain no comma or newline.
- Input amounts match `-?DIGITS[.D[D]]`, have at most two decimal places, and are nonzero.
- Stored amounts are integer cents.
- Dates are real calendar dates in `YYYY-MM-DD`.
- Account and category references must exist.
- Transaction ids must be valid and unique where created.
- No resulting account balance may be negative.
- A rejected operation writes nothing.

## Atomic Preflight

Loaders, posts, amendments, deletes, and transfers first validate all rows and calculate affected balances. Only after the full operation passes may the service call persistence writes, using one transaction for multi-row operations.

# FEATURE: Bulk Reference Loading

| Field       | Value |
|-------------|-------|
| Version     | 20261020 V1 |
| Description | Loads account and category CSV files atomically after complete validation. |
| Depends On  | ARCHITECTURE.md, DATABASE.md, FEATURE-Persistence-Lifecycle.md, FEATURE-Validation.md |
| Provides    | ledger load accounts, ledger load categories |
| Consumes    | domain validation, relational ledger schema, persistence operations |

## Questions

- None.

## Purpose

The reference loaders import accounts and categories from CSV files whose headers exactly match the declared column order.

## Workflows

`ledger load accounts <csv>` expects `account,name`. `ledger load categories <csv>` expects `category,description`. The entire file is parsed and validated before any row is inserted.

Successful loading emits:

```text
table,loaded
<table>,<rows>
```

Duplicate keys, malformed rows, invalid text, unreadable files, or mismatched headers reject the command without partial writes.
